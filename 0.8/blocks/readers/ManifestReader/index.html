ManifestReader¶

Block · readers · linecaster.blocks.readers

Reads one page per image of each item's manifest: IIIF Presentation 2 or 3, or METS with MODS (also inside an OAI-PMH response).

An item's listing that takes over LISTING_TIMEOUT (60 s) or fails is a warning and a stat (reuse_listing_timeouts, reuse_listing_errors), and its pages are fetched again. Not with existing_ocr (its OCR files would need fetching anyway).

The items are ranked from the entries' item ids before anything is fetched; a page's id (<item_id>_<sequence:04d>) needs its manifest, so computing the sample reads the manifests of the items in rank order, only as far as the rule reaches (every one with per_item alone), and an item whose manifest cannot be read stops it (the sample would depend on the failure). With manifest_folder each manifest it read is saved there with an index (SAMPLE_INDEX), and the tasks, and a later launch computing the sample again, read those copies instead of fetching them again. The sample's items are divided over the tasks as the entries would be (an item whole in its task); only their sample pages' images are requested. A IIIF Collection entry is a PipelineConfigError (list its manifests). Default: every page.

Not with existing_ocr either.

Behavior¶

Entries:

  • without manifest_key: manifests: the files under data_folder matching glob_pattern, or the lines of paths_file (a manifest URL, or a path relative to data_folder), distributed over tasks in turn ([rank::world_size]) the way datatrove distributes files;
  • with manifest_key: Parquet item tables (the files matching glob_pattern, or a paths_file listing them), one item per row: its manifest link in manifest_key (a URL, an absolute fsspec path, or a path relative to data_folder), its id in item_key (optional), and, with read_metadata, every other column in the metadata of each of its pages. The rows of all tables, not the files, are divided over the tasks in equal shards (linecaster.blocks.readers.tables), so one table works with any number of tasks.

auto_tasks is the task count for about ITEMS_PER_TASK items per task, or one item per task with task_per_item (pipelines/harvest.py), which linecaster.runtime.run uses for a pipeline without engines.

A manifest is one entry, so an item's pages stay in one task (whole_items). An entry that is a IIIF Collection stands for its manifests, each an item named by its own link (a table's item_key does not apply to them); a collection listed in it, or a paged one, raises NotImplementedError (one level).

Each page adds image and metadata; with existing_ocr also transcription_file. Pages: item_id from item_key, else from the manifest entry (manifest_item_id: the last path segment that is not a generic manifest name); sequence the page's 1-based position among the manifest's pages with an image; page_id <item_id>_<sequence:04d>; image.uri the URL the image came from. metadata["manifest"] keeps the format, the manifest's URL, id, label, rights, required statement, identifiers and descriptive metadata, the page's own id and label, and the image request. Images are requested at full size (IIIF through the image service, iiif_format/iiif_quality in http; METS from the first image file group in mets_image_groups), with the fallback URL on 404.

With existing_ocr, a page's own OCR (ALTO or hOCR the manifest links: METS FULLTEXT, IIIF seeAlso / rendering) is fetched too, as a second media of the document (type document, metadata["format"] alto or hocr): a TranscriptionConverter after the reader reads it into the transcription ocr_original (the builder puts one there when the pipeline has none), and ImageFilesWriter(ocr_folder=...) writes the bytes.

A manifest that cannot be read or parsed, an image or OCR file that fails after its retries, or a response that is not an image is logged and counted (manifests_failed, pages_failed, pages_not_images, ocr_failed), and the task goes on.

Pages are requested ahead, across manifests, as many as keep the rate limits busy (linecaster.net.http.prefetched), through one HTTPFetcher.shared per process and host's settings (linecaster.net.policy.Fetchers: http, and with http_policy the policy's for each URL's host, for the manifests, the images and the OCR files alike), so the rate limits hold across the tasks a worker runs one after the other; they go on as their images arrive, so a slow request delays only its own page (an item's pages can leave out of order; sequence keeps their place).
