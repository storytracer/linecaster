Architecture¶

What linecaster is made of and how a run fits together. Terms are the glossary's; contracts, the builder, failures and the run record are in pipelines, models, presets, recipes and engines in the catalog, the page record in the data model.

What linecaster is¶

An open, modular text-recognition suite for print and handwriting (OCR and HTR, old and new documents). It combines layout, line, text, table and formula recognizers with post-processing (dehyphenation, recomposition, normalization) into reproducible datatrove pipelines that turn page images into text: the text as written, readable variants next to it, ALTO, PAGE-XML and hOCR on request. It is a generalist tool: built on protocols (HTTP, S3/fsspec, OAI-PMH, IIIF), formats (ALTO, PAGE-XML, hOCR, Parquet, JSON Lines) and standards (METS/MODS, Unicode), it depends on no collection, site, institution or project. Everything that produces text from images lives here; evaluations and project pipelines (derivatives) are built on top of it.

Packages¶

Package Holds

linecaster.text the text transforms: Unicode, typography, recomposition, the text variants

linecaster.engines the built-in engines: the rule-based steps and the single-region layout
linecaster.blocks the blocks by family (blocks)
linecaster.backends InProcess, Served, Chat

The first five load neither datatrove nor saturate, nor linecaster's blocks or runtime (tests/test_import_rule.py), so derivatives can use the data model and the formats without the pipeline machinery. datatrove and saturate are required dependencies, datatrove with its io and s3 extras (s3:// paths work everywhere), and so is httpx (http(s):// through linecaster.net); engines, Ray and PDFium are not (engine packages and extras).

Blocks and backends¶

A block is a datatrove PipelineStep with a contract; a pipeline is a list of blocks run by a datatrove executor. Each family is a subpackage of linecaster.blocks (blocks has a page per block).

Model blocks (ModelBlock: LayoutDetector, LineDetector, LineRecognizer, TableRecognizer, FormulaRecognizer, PageRecognizer, RegionRecognizer) each have a backend:

  • InProcess("pkg:Class", **kwargs) (or a preset ref) loads the engine in the worker, in warm_up() before the first page; a loaded engine is never pickled. In-process is always available and is the parity reference.
  • Served(endpoint, model=name) and Chat(preset, endpoint) (a VLM) stream pages through saturate (AdaptiveClient and through()): a window of pages in flight, adapted to the server's queue gauges and 429s; results passed on as they finish; secrets as EnvVar. The streaming exists once, in ModelBlock.

A page that failed a step carries doc.metadata["errors"], passes later model steps at once and goes to rejects/; more failures than the error budget fail the task (pipelines). Library code raises linecaster.errors, never SystemExit.

Rule blocks (RuleBlock: Typographer, Recomposer, Composer, CharacterNormalizer; and ImageConverter) run a built-in engine of a rule-based step in the pipeline's process, picked by a preset.

One page per request¶

A request carries one page; engines batch only within a page (kraken batches a page's lines). A page's result depends only on the page, never on what else is in flight, so runs are deterministic whatever the executor, the number of tasks or the backend.

Servers¶

  • linecaster serve hosts engines: stateless (no state between requests), one worker per model (several replicas per model were measured at +7–10 % and removed; NOTES.md), each with a bounded queue (--max-queue; a full queue answers 429 with Retry-After). Routes: POST /v1/linecaster/{step} (the image and the transcription so far in, the transcription with its part and the call's annotator added out; both linecaster.page/3 annotation sets), GET /v1/models, /health (status and protocol, the transcription format: linecaster.page/3) and vLLM-shaped /metrics (the gauges saturate reads). A Served client asks a server that already answers for its protocol when it warms up and refuses one that names another format or none (ServerError): both sides run the same linecaster version. Built-in engines are not served: they run in the pipeline's process.
  • VLMs run behind OpenAI-compatible servers (vLLM, SGLang, hosted endpoints): PageRecognizer and RegionRecognizer on the Chat backend, on /v1/chat/completions, served only. PageRecognizer also runs a page engine (an engine whose unit is the page) on the InProcess or Served backend: a vendor's package in the worker (Indra OCR), a vendor's package attached to a vLLM server (Surya OCR), or a client of a vendor's page pipeline behind its own HTTP API (Falcon-OCR, OXR). A VLM is a catalog preset (engine chat.v1; its data: revision, prompt, sampling, serve block) plus an adapter in linecaster.adapters.ADAPTERS (its code: the request, the parsing; chat_model(<preset>)).
  • Servers inside a task (one GPU per HF Job): the server blocks ModelServer (linecaster serve) and ChatModelServer (vLLM or SGLang) start the server through saturate's Engine and go last in the pipeline, after the writer: datatrove chains generators, and only the last one lives until every page is written. Each task starts its own servers. ModelServer(script=...) starts a pipeline script's serve with uv run --script. ServiceServer starts the service a page preset's serve block names: vllm serve on the pinned checkpoint (fetched and checked) for an engine package that attaches to vLLM, or a vendor image's entrypoint (with the weights downloaded to the folder it reads first), ready once its health URLs answer; it runs without the pipeline's environment, in the image's own. A vendor's entrypoint listens on the image's fixed ports: one service per machine.

Engines¶

An engine is a class with a versioned id (catalog). Engine packages live in engines/<engine>/, each its own package: linecaster-kraken, linecaster-paddlex, linecaster-tesseract, and the page engines' linecaster-indra, linecaster-surya and linecaster-services (the clients of Falcon-OCR's and OXR's services). An engine class (<Provider><Step>Engine) has engine_id (the entry point's name in linecaster.engines), step, capabilities (unit, produces), an Options model (its keyword arguments; a preset's weights besides), load() and __call__(image, transcription, **params) -> Transcription (the page image as an RGB array, or the image file's bytes for an engine whose image_input is "bytes", and the transcription so far, returned with its part added). Engines with weights load exactly the pin (weights, linecaster.catalog.fetch). PaddleX's models load from the pinned snapshot (create_predictor(model_dir=...)); small-models-for-glam/kraken-blla-base (the BLLA base model of September 2026) is pinned in linecaster_kraken.models, and no engine uses it. Engine packages carry code only; their presets and models are in linecaster's catalog. They import from linecaster only linecaster.data and the engine API (linecaster.engines.api: the Engine protocol, Capabilities, the weight helpers), have versions of their own with a range of linecaster releases, and their tests in engines/<engine>/tests/ (catalog).

Tests¶

uv run pytest runs the core's tests, one after the other; uv run pytest -n auto (pytest-xdist, in the dev group) runs them on every core. Tests marked gpu or network (linecaster.testing.markers: gpu, network, slow; --strict-markers) skip where the device or the network is missing. The CI workflow (.github/workflows/ci.yml, CPU only, no secrets, uv's cache kept between runs) runs uv sync --locked --all-extras (the extras' readers are tested and documented too), uv run pytest -n auto -m "not gpu and not network", linecaster catalog verify, linecaster docs and the site's strict build (the generated pages are not in git, so CI writes them and a broken reference in them fails the build). The docs workflow (.github/workflows/docs.yml) writes them too and publishes the site, built by Zensical, with mike (Zensical's fork) on the gh-pages branch, which GitHub Pages serves (https://storytracer.github.io/linecaster/): a release tag v<major>.<minor>.<patch> as version <major>.<minor>, with latest (the site's default) moved to it; nothing else is published. The engines' environments are too large for it (torch): their tests (engines/<engine>/tests/) and the PEP 723 test scripts (tests/test_engines_catalog.py, tests/test_page_engines_catalog.py, tests/test_line_recognizers.py) run locally. Every built-in engine and every public block passes the conformance checks of linecaster.testing (check_engine: the engine protocol; check_block: the contract against what the block does to sample pages, to_dict(), pickling, warm_up(), failed pages).

An engine package's tests run in an environment that has the engine: uv run tests/test_engines_catalog.py engines/<engine>/tests. tests/test_engines_catalog.py holds kraken, PaddleX and Tesseract for the catalog's line-recognizer presets.

Recipe scripts¶

A catalog recipe is YAML (src/linecaster/catalog/data/recipes/<id>.yaml: its presets, editions and hash). Its environment and entry point is a uv script of its own, recipes/<id>.py: a PEP 723 block with linecaster[ray] and exactly the engine packages its presets need (recipe → presets → engines → packages: linecaster.catalog.code.recipe_packages), its lock, and a body that only calls linecaster.runtime.run.recipe(__file__, "<id>"), which runs the recipe through its pipeline shape with --recipe set. The pipeline scripts depend on no model choice (pipelines/transcribe_modular.py has PaddleX and Tesseract); the recipes bring theirs (recipes/squiddle.py: kraken and PaddleX).

The recipe scripts take linecaster and its engine packages from the main branch on GitHub, so a script runs from its URL with no checkout (uv run https://raw.githubusercontent.com/storytracer/linecaster/main/recipes/squiddle.py IMAGES OUT, hf jobs uv run <URL> ...) as well as from one (uv run recipes/squiddle.py, uv run launch.py squiddle). A run from the URL resolves the header afresh, and its run record names the script recipes/<id>.py (uv runs a temporary copy); a run from a checkout uses the script's lock, whose linecaster commit moves when it is relocked. Their HF Jobs need no --commit: jobs.dependencies installs linecaster from main with the lock's versions as constraints. With --endpoint the served engines need not be installed in the client's environment. To preview the site from a checkout: uv run linecaster docs, then uv run --group docs zensical serve.

Pipeline scripts¶

There are no environment folders: a pipeline is a self-contained uv script in pipelines/ (a PEP 723 block, a <script>.py.lock next to it, uv run <script>) that runs one pipeline shape with slots, one script per shape, never one per machine. The shape is library code, linecaster.pipelines.<name> (its options, engines, blocks, pipeline id and slots), so a derivative's script can run it in its own environment with its own defaults (pipelines):

Script Pipeline id Does
harvest.py harvest.v1 downloads page images (and a library's OCR, manifests) once into item folders, plus page records
transcribe_modular.py transcribe_modular.v1 lines and a recognizer, optionally layout, tables, formulas, then post-processing; every step a preset the user picks; PaddleX and Tesseract, no kraken
transcribe_vlm.py transcribe_vlm.v1 a VLM per page or per layout region
transcribe_page.py transcribe_page.v1 a page engine per page, with the service its preset names
bind.py bind.v1 item texts and item documents from page records
convert.py convert.v1 page images converted to JPEG, JPEG 2000, PNG or WebP by an image preset, on NVIDIA GPUs where the machine has them

linecaster.runtime.run.main gives every pipeline the same command line: --on local|ray|hf-jobs, --backend in-process|served, --endpoint (a running server), serve (linecaster serve with the script's models), ray (Ray's CLI from the script's environment). Slots have no default presets: every slot is picked, or a recipe fills them (--recipe); launch.py runs a recipe or a page preset by name (catalog). Each script's page in the catalog's docs lists its slots and options.

Script environments: the repository is not a uv workspace (engine pins conflict). A script lists what it needs itself: linecaster with the extra every pipeline uses (ray for --on ray and ray start) and its engine packages (convert.py and the transcription scripts also nvimgcodec: NVIDIA's GPU codecs, used where the machine has a GPU); s3:// paths need no extra (the core installs datatrove's s3 extra, s3fs). A source is declared by the package that needs it, and uv lock applies the sources of path and git dependencies too: the kraken fork by linecaster-kraken, and stubs/opencv-contrib-python (the headless build of the version PaddleX pins; one cv2) by linecaster-paddlex. tests/test_scripts.py checks sources, locks and wheels for both machines (uv's required-environments does not work in scripts).

torch is never a dependency of the core. Only linecaster-kraken pins it (torch==2.14.0: kraken's upper bound is <=2.14, and the PyPI 2.14 wheels are the CUDA 13 build on Linux, aarch64 and x86_64), and only environments with linecaster-kraken are bound by that pin; the others take what their own dependencies allow. Each lock's torch is fixed in tests/test_scripts.py (TORCH), so it changes only on purpose:

Environment torch Why
tests/test_engines_catalog.py 2.14.0 linecaster-kraken's pin
pipelines/transcribe_page.py, tests/test_page_engines_catalog.py 2.14.0 surya-ocr's (>=2.7,<3), not pinned: the version it was locked at
tools/cuda_probe.py 2.14.0 its own pin: it probes the CUDA build of linecaster-kraken's torch on a Jobs host
pipelines/transcribe_modular.py, transcribe_vlm.py, harvest.py, bind.py, convert.py, launch.py, tests/test_line_recognizers.py, linecaster's own (uv.lock) none no engine there needs it

Executors and Jobs¶

--on Executor
local datatrove's LocalPipelineExecutor
ray RayGPUExecutor for stages with servers and single-stage pipelines with engines (each task holds one GPU; without --tasks, 4 tasks per GPU of the cluster, and one per GPU where each task starts a VLM's server, which takes minutes), RayExecutor (datatrove's RayPipelineExecutor) otherwise, on CPUs (an item stage, a harvest; extra [ray]); both stop the run at an error that is not the pages', fail a launch that left tasks unfinished, and check first that a live node can run a task
hf-jobs JobsExecutor: datatrove's JobsPipelineExecutor with JSON-lines logs; GPUJobsExecutor for multi-GPU flavors

datatrove's JobsPipelineExecutor is experimental and dill-pickles the pipeline, so the launching machine and the Jobs run the same Python minor version (3.12). uv run outside a project drops [tool.uv.sources]: linecaster.runtime.jobs.dependencies(commit, script) spells out a pipeline's dependencies and sources as URLs, the installed packages' own sources from the script's lock (the commit must be pushed), and pins every other package at the lock's version; each Job runs a uv script that carries the pins and the script's overrides, which uv run --with would ignore (pipelines).

Workers that share something beyond their tasks (a proxy list, whose proxies each worker may use only while no other does) agree through the broker, a folder any executor's workers can reach, on any storage datatrove supports: leases say who holds what, marks what is unavailable until when, and a worker is a slot of its machine that outlives the processes (on Ray every task is one) that take it over.

The run layout¶

One job is one pipeline for one batch on one executor; resume is datatrove's, per task, so tasks stay small. A pipeline reads the previous folder and writes complete page records with one more part filled in:

Folder Holds
originals/ the delivered images and files; never modified
OUT/pages/ page records (PageJsonlWriter, PageParquetWriter), bucketed by item id: a whole item in one file, so no joins
OUT/rejects/ every page that carries errors (RejectWriter, put before the first writer by the builder): key, field, error, raw value
OUT/logs/ datatrove's completion markers, logs and stats; OUT/logs/broker/, the broker by default
OUT/traces/ the traces (tracing)
OUT/run.yaml the run record (pipelines)
OUT/sample.parquet the sample a run read, one row per page in sample order (pipelines)
OUT/manifests/ the manifests a sample read (with sample.jsonl), or a harvest saved

PageRecordReader reads page records of linecaster's writers, fetching images again by URI (uri_map for local copies). Checks like PageValidator record on the page why it failed.

Readers follow datatrove's conventions (BaseDiskReader: data_folder, paths_file, glob_pattern, limit/skip per task; files distributed over tasks in turn, Parquet tables by rows in equal shards, linecaster.blocks.readers.tables, so a table needs no splitting): ImageFolderReader (image files), ImageParquetReader (an image column: bytes, an HF image struct or a path), ManifestReader (IIIF or METS, parsed by linecaster.formats.manifests, its files fetched through linecaster.net.http; a manifest, or a row of a Parquet item table, is an entry, so an item stays in one task; a IIIF Collection entry is its manifests, one level; existing_ocr fetches a library's OCR as a document media, which a TranscriptionConverter reads as ocr_original, the builder adding one when missing), PdfReader (PDF files as items, pages rendered with pypdfium2, extra [pypdfium2]) and PageRecordReader. Readers that fetch over http(s) request ahead in a window that grows while no request waits for the rate limits (linecaster.net.http.prefetched), through one fetcher per process and configuration, so the limits hold across a worker's tasks; ImageParquetReader and ManifestReader suggest a task count from their input (auto_tasks), which a pipeline without engines runs with (pipelines).

The workflow is harvest → transcribe → bind: pipelines/harvest.py downloads images (and OCR, manifests) once into item folders plus page records, the transcribe pipelines read those with --pages, pipelines/bind.py makes item texts and documents. An item's pages can land in different tasks; item-level steps are a second stage over item shards (--item-shards N writes OUT/pages/<shard>/<rank>, pipelines/bind.py reads whole shards), as datatrove's own multi-stage pipelines read per-bucket folders (pipelines).
