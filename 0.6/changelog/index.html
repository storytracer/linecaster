    Changelog¶

    All notable changes to linecaster. The format follows Keep a Changelog; each release lists upgrade notes first, then additions, changes, deprecations, removals and fixes. Versions follow the tags; the first is v0.1.0.

    0.6.0 (2026-11-12)¶

    Upgrade notes¶

    • The engine packages (linecaster-kraken, -paddlex, -tesseract, -surya, -indra, -services, 0.1.5) accept linecaster <0.7.
    • Model blocks decode page images on an NVIDIA GPU where the machine has one and linecaster[nvimgcodec] is installed (--image-decode auto, the default): JPEG, JPEG 2000 and TIFF in 8-bit gray or RGB, for in-process engines, for chat adapters' requests and region crops, and in linecaster serve. A GPU rounds a lossy image's pixels differently from Pillow (on test images up to 1 step of 255 for lossy JPEG 2000 and 3 for JPEG; lossless JPEG 2000 is exact), so a page's text can differ slightly from a run that decoded with Pillow; each step names its decoder (measurement decoder). --image-decode cpu (build(..., image_decode="cpu")) keeps Pillow's pixels everywhere, as before; without nvImageCodec nothing changes. The transcription pipeline scripts install linecaster[nvimgcodec]. Evidence (NOTES.md, 2026-11-12): squiddle over 500 lossy JPEG 2000 pages on 8 RTX A6000 ran in 66 s instead of 110 s; the text changed on 57 of the 452 pages the GPU decoded (similarity 0.994 on those), none on the 48 it refused.
    • linecaster.blocks.base.page.DECODED_KEPT is gone: the decoded pages are kept by linecaster.images.pixels (KEPT). decode_rgb(data, accel=None) takes the decoding as an optional second argument.

    Added¶

    • linecaster.images.pixels: page images as engines receive them, plain RGB (convert("RGB"), no colour handling) decoded once per process, on the GPU where it can (decode_pixels with the decoder and any GPU fallback, decode_rgb, rgb_image for code that resizes or encodes the page, set_decoding for the process's choice and device). Model blocks set it from image_decode (--image-decode), on the worker's GPU, and count gpu_decoded, cpu_decoded, gpu_decode_refused and gpu_decode_errors.
    • linecaster serve takes image_decode with a request (served blocks send theirs) and records the decoder on the step it returns.
    • Measurement decoder: what decoded the page image a step read; served blocks count gpu_decoded/cpu_decoded from the server's.

    Changed¶

    • Chat adapters and RegionRecognizer build their requests from the shared pixels instead of decoding the file again: a page an in-process block before them decoded is not decoded twice.
    • linecaster.images.accel.gpu_available asks the driver only where nvImageCodec is installed: no CUDA call without it.

    0.5.13 (2026-11-12)¶

    Upgrade notes¶

    • webp-lossy-q80 resolves to edition 3: libwebp's method 4 again (libwebp's and Pillow's default) instead of edition 2's method 0. The default output changes: files about 20 % smaller, conversions slower. --set image.method=0 gives the old speed, --preset webp-lossy-q80@2 reproduces earlier runs (@1 and @2 stay resolvable).

    Changed¶

    • On Ray a pipeline with engines and no --tasks gets 4 tasks per GPU of the cluster (RAY_TASKS_PER_GPU, at most what its reader can split the input into) instead of one: a worker that is done takes the next task, so a task that holds slow pages (a run of JPEG 2000 files, say) no longer holds the run up. Each task loads its models again (a Ray task is a new process); --tasks still decides.
    • A page's image is decoded once per process for all its in-process model blocks (decode_rgb keeps the last four pages' pixels by the bytes object they came from), not once per block: a JPEG 2000 page went through Pillow's decoder for layout, lines and recognition alike (about 0.7 s each on the x86_64 machine). The pixels are the same as before (Pillow, convert("RGB"), read-only as they were); each model block counts image_decoded or image_shared, and linecaster.blocks.base.page.decodes() the files decoded.
    • The PNGs a VLM request sends (whole pages, region crops) are encoded at zlib level 1 instead of Pillow's default 6: lossless either way, so the server decodes the same pixels and no edition changes; a 2,048-px page encodes 4.3 times faster (147 against 637 ms) for about 10 % more bytes (linecaster.adapters.PNG_LEVEL).
    • webp-lossy-q80@3: method 4. Evidence (NOTES.md, 2026-11-12): a whole conversion of 10,000 lossy JPEG 2000 page scans (GPU decoding, 8 RTX A6000, 124 vCPUs, network mount) ran at 100 pages/s with method 4 against 133-138 with methods 1-2, for median files of 402 KB against 415-485 KB and the best PSNR (41.61 dB); on 40 pages method 0 gave files 27 % larger than method 4 at the same PSNR. Edition 2's evidence (4.4 times faster encoding) timed the encoder alone, which a whole run does not show.

    0.5.12 (2026-11-12)¶

    Added¶

    • harvest.py --reuse-from DIR for page-image harvests too (--parquet, --manifests; not with --existing-ocr, whose OCR files would need fetching anyway). Page records can be large and many, so each launch reads the earlier folders' records once (DIR/pages/**/*.jsonl.gz) into an index in the run's folder (OUT/logs/reuse-from.parquet: source URL, the copy under DIR/images, sha256, sorted by URL; a record with errors gives nothing; the newest folder holding a URL wins, by its run records' created), and each task (with --manifests each item) reads only the index's row groups its URLs fall in (linecaster.blocks.readers.earlier). A copy is checked against its sha256 (else fetched: reuse_from_mismatch, reuse_from_unreadable), read after OUT's own copy (--reuse) and before a fetch, and written into OUT under its current item and page id; its record says image.extra.reused_from and reused_from_uri, and the console counts it per folder as for resources. The key is the URL a record names, the one that was fetched: a page that came through a redirect or its fallback URL is fetched again. ImageParquetReader and ManifestReader take reuse_index, an operational parameter.

    0.5.11 (2026-11-12)¶

    Fixed¶

    • nvImageCodec prints nothing for an image its GPU decoder rejects: linecaster sets PYNVIMGCODEC_VERBOSITY=0 before importing it (a value in the environment wins, e.g. 2 for its errors and warnings). nvJPEG2000 logs each rejection at ERROR severity ([nvjpeg2k_decoder] Could not decode jpeg2k code stream - nvjpeg2k error #4 (Jpeg not supported), [pynvimgcodec] Something went wrong during decoding image #0), so only 0 silences it; the rejection stays recorded and counted by linecaster (gpu_fallback, gpu_decode_refused). A GPU decoder or encoder that did not load is said once by linecaster (its formats go to the CPU), and a failing GPU is logged once per kind of failure and counted, not logged per page.
    • Ctrl-C: after the summary and the cleanup (workers ended, unfinished tasks reported), a run prints no traceback and ends by SIGINT (run.main), so a shell loop around python pipelines/<script>.py ... stops; a second Ctrl-C ends it at once. A pool's worker processes ignore SIGINT from their first task on (the terminal sends it to all of them; one waiting for its next task printed a traceback of its own): the main process ends them, as before. Under uv run the loop still goes on: uv turns the signal into exit code 130 (astral-sh/uv#11886); trap 'exit 130' INT before the loop stops it.

    0.5.10 (2026-11-12)¶

    Added¶

    • harvest.py --items --reuse-from DIR (repeatable; ResourceReader(reuse_from=...)): a harvest into a new folder takes the files earlier harvests' folders already hold and fetches only the rest, so a changed list gets one complete folder instead of a resume whose tasks no longer fit it. The key is the source URL (an item and a name can change between versions of a list): from each folder's records (DIR/resources/*.jsonl.gz, read once per worker process; its file folders are never listed) the newest record without error and with a copy, across the folders. The copy, found at its <kind>/<item>/<file> in DIR, must match its record's sha256 (else, or when it cannot be read, the resource is fetched: stats reuse_from_mismatch, reuse_from_unreadable) and passes the same check as a download; ResourceFilesWriter writes it into OUT under its current item and name. Its record keeps the earlier fetch's fetched, final_uri, status, content_type, etag, last_modified and attempts, and adds reused_from (DIR) and reused_from_uri (the earlier copy). Order: OUT's own copy (--reuse), then the earlier folders, then a fetch. reuse_from is operational: a resume with other folders keeps the run's fingerprint. The console counts these files apart (stat reused_from) and the summary names how many came from each folder.

    0.5.9 (2026-11-12)¶

    Changed¶

    • webp-lossy-q80@2: libwebp's method 0 instead of 4 (Pillow's default): speed over size. Evidence (NOTES.md, 2026-11-12): on 100 lossy JPEG 2000 page scans at quality 80, method 0 encoded in 0.086 s a page against 0.376 s (4.4 times faster) at the same PSNR to the source (40.2 against 40.3 dB), the files 15 % larger. Edition 1 stays resolvable.

    Fixed¶

    • Whatever keeps a GPU from an image, the CPU does it (accel auto): a file its decoder or encoder rejects (as before), and now also a failing GPU (an error, too little memory, a codec that does not start), which failed the pages of its batch. Each image records it (gpu_fallback: {"decode": "refused" or "error: ..."}, the same for encode); ImageConverter counts both (gpu_decode_refused, gpu_decode_errors, gpu_encode_...) and logs the failures as a WARNING. accel gpu makes either an error. nvJPEG2000, for one, rejects code streams with the vertically causal context (code-block style 0x08).
    • On the CPU, Pillow decodes one JPEG 2000 image at a time per process: its decoder reads through Python and holds the GIL for the whole decode (pulls_fd; it sets no OpenJPEG threads), so parallel decodes in one process gained nothing and allocated OpenJPEG's buffers early. Other formats and the GPU are not held; processes decode in parallel as before.

    0.5.8 (2026-11-12)¶

    Added¶

    • Image conversion: page images (any format Pillow reads) to JPEG, JPEG 2000, PNG or WebP at full resolution, 8-bit sRGB, with the working image's colour handling, size limit and image warnings: engine image.convert.v1 (linecaster.images.transcode), presets webp-lossy-q80, jpeg-q90, jp2-lossless and png, pipeline pipelines/convert.py (convert.v1, --preset).
    • GPU acceleration where the machine has it (linecaster.images.accel, extra nvimgcodec: nvImageCodec's CUDA 13 wheels, aarch64 and x86_64): JPEG, JPEG 2000 and TIFF decoded on an NVIDIA GPU, JPEG and JPEG 2000 encoded there; everything else with Pillow. Found out per machine (auto), forced with accel gpu or cpu; each image records its decoder and encoder. linecaster images compare measures how a GPU decode differs from Pillow's.
    • ImageConverter runs its pages through four stages, fetching, decoding, encoding and writing, each with a window saturate's controller adapts (window, initial_window; max_window for decoding and encoding, max_io_window for fetching and writing), a page keeping its place in one stage until it has one in the next, a GPU per worker process; it writes under a temporary name and renames (on object storage directly), uploads to a Hugging Face bucket in batches (HfApi.batch_bucket_files), skips files that are there already (skip_existing), and keeps the input's order.
    • ImageFolderReader(read_images=False) (run.reader(read_images=False)): pages carry only their images' addresses, for a block that reads the files itself.

    Changed¶

    • --cpus-per-task (Ray) defaults to 12 or a pipeline's own share: convert.py reserves one GPU per task (RayGPUExecutor, since Ray hides the GPUs from a task that reserved none) and the launching machine's CPUs divided by its GPUs, where it has GPUs.
    • ImageConverter's display name is 🖼️ image converter (was 🖼️ image converter (lossless WebP)); the working image is written as before.

    0.5.7 (2026-11-12)¶

    Fixed¶

    • Image warnings: a fault an image is read around no longer fails it. A PNG whose optional (ancillary) chunk fails its checksum (e.g. a damaged ICC profile, iCCP) is read without that chunk, as libpng and browsers read it; Pillow alone refused the whole file, so the harvest failed such files as not image: UnidentifiedImageError and they counted toward the host's breaker. Such faults, what Pillow warns about while reading (e.g. corrupt EXIF), EXIF that cannot be read and an ICC profile that cannot be applied are now image warnings (linecaster.images.image_warnings): the harvest keeps the file unchanged and records them in its fetch record (warnings), the conversion in the page image's extra (warnings, stat image_warnings), both logged as a WARNING. Every place that decodes image bytes reads through linecaster.images.open_image, and the chat adapters that pass a page's bytes on unchanged send them without the damaged chunks; engine packages get drop_damaged_png_chunks from the engine API. A fault that keeps the pixels from being read still fails.

    0.5.6 (2026-11-12)¶

    Fixed¶

    • Shared proxies keep a host's rate limit when they change hands. A worker that gave a proxy back (its fair share, a swap, a block) forgot its next turns there, and the worker that claimed it could send at once, up to an interval earlier than the limit allows, while the old owner's requests already on their way still went out. The old owner now marks the proxy's next free turn at each host in the broker (scope turn-<host>, ending at that turn), and the new owner starts there no earlier. linecaster broker status and the count of available proxies at a launch leave these marks out.
    • A recipe script run from its URL is recorded as recipes/<id>.py (the run record's script.path, and the console's title) instead of the name of uv's temporary copy (squiddleXXXXXX.py). In a checkout its path there is recorded, as before.

    0.5.5 (2026-11-12)¶

    Changed¶

    • Repair passes escalate: repair_max_tokens takes a list of rising caps, one repair pass each (a number stays one pass). A repair that stops at its cap is sent again with the next cap; the page keeps the first completion that finished (stop), else its first, and extra["kept"] numbers the kept pass from 1. lightonocr-3-0.8b@3 now repairs at [8192, 12288] (twice and three times its 4096): its edition 3, released in 0.5.4 with one repair at 12,288, was replaced in place (the 0.5.4 release of it was incomplete); its run records' hash changes. StepInfo.settings["repair"]["max_tokens"] is now always a list. The second repair deviates from the reference script (uv-scripts/ocr lighton-ocr3-saturate.py at e2b0aa5: one repair, 8192 suggested; its temperatures, 0.2 and 0.1 for the repair, are kept). Evidence (NOTES.md, 2026-11-12): on a 33-page trial of table and formula pages, one RTX A6000, vLLM 0.30.0, 5 to 6 pages stopped at 4096; a single repair at 8192 finished 4 of 5 in one run and 3 of 5 in another, the dense table stopping at 8192 both times; it finished after 8,958 tokens with a cap of 12,288, and with [8192, 12288] every page finished.

    0.5.4 (2026-11-12)¶

    Changed¶

    • lightonocr-3-0.8b@3 turns the repair pass on at 12,288 tokens (settings.repair.max_tokens), otherwise as @2: a page whose completion stopped at 4096 tokens is sent once more, only then and only once. lightonocr-3-0.8b without an edition now resolves to @3, so its runs write a second pass for truncated pages and get a new pipeline_sha256; --recognition lightonocr-3-0.8b@2 (or --set recognition.repair_max_tokens=0) keeps the former behavior, and a resume into a run of @2 needs the edition named.

    0.5.3 (2026-11-12)¶

    Added¶

    • --uri-map PREFIX=REPLACEMENT (repeatable) for --pages: image URIs in page records rewritten before reading, for images that moved since the records were written (PageRecordReader's uri_map).
    • The repair pass for chat page presets: with repair_max_tokens set, PageRecognizer sends a page whose completion stopped at max_tokens (finish_reason length) once more, at once and into the same window: the same request (image, prompt, top_p) with max_tokens raised to repair_max_tokens (at most the served context minus the page's prompt tokens; the context from the server's /models max_model_len, else the preset's --max-model-len) and temperature repair_temperature (0.1). The page keeps the second completion where it finished, else the first; there is no third request. The procedure is the reference script uv-scripts/ocr lighton-ocr3-saturate.py at e2b0aa5's, which repairs at the end of a run. Where the context leaves no more room than the first request had, no repair is sent (repair_skipped); a run warns at the start when repair_max_tokens and a page's largest prompt do not fit the context. Stats repair_sent, repair_stop, repair_length, repair_kept, repair_skipped, repair_errors next to finish_length (first requests).
    • A repaired page's transcription records every request in extra["passes"] (raw, finish_reason, tokens, the max_tokens, temperature and top_p it was sent with, preset) and the one it holds in extra["kept"]; extra["raw"] and extra["finish_reason"] are the kept one's. The step sums the tokens and lists them per request (new measurements pass_prompt_tokens, pass_completion_tokens) and has repair in its settings.
    • PageRecognizer(repair_only=True) and pipelines/transcribe_vlm.py --pages OUT/pages --repair-only: the repair pass over page records written earlier, also by earlier releases (finish_reason in extra, no passes); only the pages that stopped at max_tokens and have no repair yet get a request, every other page is written unchanged (repair_not_needed).
    • The chat engine's options (ChatAdapter.Options: max_tokens, temperature, top_p, repair_max_tokens, repair_temperature) over a preset's settings: Chat(..., overrides={...}), chat_model(..., overrides=...) and pipelines/transcribe_vlm.py --set recognition.<option>=<value> (--set layout.<option>=... for the layout model). The values that differ from the preset's are recorded with the adapter (overrides) and change pipeline_sha256. repair_max_tokens must be larger than max_tokens.
    • Chat presets may state settings.repair (max_tokens, temperature).
    • lightonocr-3-0.8b@2: --max-model-len 18000 (LightOn's README), otherwise as @1, with the repair settings stated (off). @1 stays resolvable. LightOnOCR3Adapter.max_prompt_tokens() (4,160 tokens at 2048 px).
    • ChatModelServer starts vLLM with VLLM_USE_FLASHINFER_SAMPLER=0 on a machine without a CUDA toolkit (no nvcc on the server's PATH, neither CUDA_HOME nor CUDA_PATH) unless the variable is set: FlashInfer's sampler compiles its kernels at first use and fails there ("Could not find nvcc"). Logged once.
    • fake_chat_server(models=[...]) answers GET /v1/models.
    • Block.unhashed_defaults: parameters added to a released block whose default keeps the old behavior; pipeline_sha256 leaves them out at that default.
    • Samples: --sample N, --sample-per-item K, --sample-items M and --sample-seed S (default 0) read a fixed sample of the input, for IMAGES (--item-from-parent for items), --parquet, --manifests and --pages. Items are ranked by H(f"{seed}\t{item_id}"), pages within an item by H(f"{seed}\t{item_id}\t{page_id}") (H: the first 8 bytes of SHA-256, unsigned big-endian; ties by id), and the pages in (item rank, page rank) order are cut after M items, K pages per item and N pages (linecaster.sample/1). The sample comes from the ids alone before any image is read (Parquet: the id columns only; manifests: the manifests of the items the rule reaches, saved to OUT/manifests/ with an index and read back by the tasks), is the same whatever --tasks, and is recorded in the run record's new sample section and in OUT/sample.parquet. A resume with another sample is refused.
    • linecaster.data.sample (standard library only): SampleRule, select, sample_pairs, item_hash, page_hash and the listing and sample hashes, for derivatives that recompute a sample.
    • The readers' sample parameter (ImageFolderReader, ImageParquetReader, ManifestReader, PageRecordReader) and sampled().
    • linecaster sample [IMAGES] OUT ...: the sample of an input without a run (OUT/sample.parquet).

    Changed¶

    • lightonocr-3-0.8b (without an edition) now means @2.
    • ModelBlock's served loop lets a finished request ask for a second one (_second_request, _second_done).
    • The glossary's "sample" of tracing is now the "trace sample"; "sample", "item rank" and "page rank" are the run's sample. --trace-sample is unchanged.
    • Parquet slices of one row group are read with one read of the row group.

    Fixed¶

    • The chat recognizers' docstring said a completion cut off at max_tokens is "on page OCR nearly always a repetition loop"; a dense table often only needs more tokens and finishes with more room.

    0.5.2 (2026-11-11)¶

    Upgrade notes¶

    • The recipes run in their own scripts, recipes/<id>.py. Who is affected: anyone who ran the squiddle recipe with pipelines/transcribe_modular.py --recipe squiddle (since 0.5.0 that stopped with "needs engine 'kraken.recognition.v1', which is not installed", or needed --backend served --endpoint), and anyone who ran item-texts with pipelines/bind.py --recipe item-texts, which still works. What to do: run uv run recipes/squiddle.py IMAGES OUT (or uv run launch.py squiddle IMAGES OUT, which now starts that script), or without a checkout uv run https://raw.githubusercontent.com/storytracer/linecaster/main/recipes/squiddle.py IMAGES OUT. The options are the same; slots on top of the recipe are still recorded as overrides.

    Added¶

    • A uv script per catalog recipe, recipes/squiddle.py and recipes/item-texts.py: a PEP 723 block with linecaster[ray] and exactly the engine packages the recipe's presets need (squiddle: linecaster-kraken, linecaster-paddlex; item-texts: none), its lock, and a body that calls linecaster.runtime.run.recipe. The scripts take linecaster from its main branch on GitHub, so they run from their raw URL with no checkout, as from one; locally, on Ray (ray), as a server (serve) and on HF Jobs (no --commit needed). The recipes stay YAML in the catalog, with their editions and hashes.
    • linecaster.runtime.run.recipe(script, recipe_id): a recipe script's body. It runs the recipe through its pipeline shape; an edition of the same recipe (--recipe squiddle@1) may be given, another recipe may not.
    • linecaster.catalog.code.recipe_scripts and recipe_packages (recipe → presets → engines → packages). tests/test_scripts.py checks that every recipe has its script, that the script lists exactly those packages, and that its lock is current.

    Changed¶

    • uv run launch.py <recipe> ... starts recipes/<recipe>.py instead of the pipeline script the recipe names.
    • A missing engine's error names the recipe script that installs it when no pipeline script does (kraken: recipes/squiddle.py).
    • linecaster.runtime.jobs.needs_commit: a script in the checkout that takes linecaster from git (a recipe script) needs no --commit; one that takes it by path (a pipeline script) still does.
    • The generated recipe pages show the recipe's script and its URL.

    0.5.1 (2026-11-11)¶

    Fixed¶

    • ResourceReader takes DjVu files: a response served as image/vnd.djvu (or image/x-djvu) was checked as an image, which an image library cannot open, so every DjVu resource failed. A DjVu response is now checked by its signature (AT&TFORM) and kept as .djvu; a resource kind or URL naming djvu expects the format, so an HTML page in its place still fails as UnexpectedHTML. A DjVu file served as text/html is no longer taken for an HTML page (linecaster.net.http.DATA_MAGIC).
    • A fresh pause counts exactly its wait toward max_pause (Pause.hit): it was computed as now + wait - now, which floating point can make a hair shorter on a machine whose clock reads high.

    0.5.0 (2026-11-11)¶

    Upgrade notes¶

    • The pybookget extra is gone: linecaster reads IIIF Presentation and METS/MODS manifests itself (linecaster.formats.manifests, on lxml) and fetches over http(s) with its own HTTP layer (linecaster.net: httpx with HTTP/2 and fake-useragent, both core dependencies now). Who is affected: anything that asks for linecaster[pybookget] (a derivative's script or project, uv sync --extra pybookget, which fails; uv warns about the unknown extra). What to do: drop the extra (linecaster[ray,pybookget] becomes linecaster[ray]) and relock; a derivative that imports pybookget itself lists it as its own dependency. The relocked environments lose pybookget, pyrate-limiter and tenacity, and those that had no http(s) before (bind.py, launch.py, the test scripts) gain httpx's HTTP/2 packages (h2, hpack, hyperframe) and fake-useragent; torch is unchanged everywhere.
    • A reader's http settings (and HTTPFetcher(**config)) are the fields of linecaster.net.http.HTTPConfig, with the same defaults as before (HTTP_DEFAULTS), instead of any field of pybookget's Config. Who is affected: code that passes a pybookget-only field (show_progress, retry_multiplier, cookie_file, header_file, ...): it is now a TypeError. What to do: leave the field out. The wait after the n-th failed attempt is retry_wait_min * 2**(n-1) seconds, at most retry_wait_max, on the direct path as through proxies; with the defaults (retry_wait_min 2) that is the wait it was, and only a changed retry_wait_min waits otherwise.
    • The HTTP policy has a new schema, in three levels (http): every request at the root, the proxy path's own section proxies:, and hosts:. What blocks is declared once for both paths (block_on, default [429], statuses and html): direct a block pauses the worker's requests to the host, through proxies it leaves the proxy out there. Who is affected: every policy file with pause_on, blacklist_on, blacklist_ttl, blacklist_threshold, proxies_per_worker or proxies as a plain path: the run stops at startup with a PipelineConfigError that names the line to write. What to do: pause_on: [429, 503] becomes block_on: [429, 503]; blacklist_on: [403] becomes block_on: [429, 403] (the statuses of both in one list); proxies: proxies.txt becomes proxies: {file: proxies.txt}; proxies_per_worker: 1, blacklist_ttl: 72h and blacklist_threshold: 2 become proxies: {per_worker: 1, block_ttl: 72h, broken_after: 2}. pause_on: [] (429s retried on the direct path) becomes block_on: [], which now also leaves 429s through proxies to the retries; keep block_on: [429] and set max_retries if a 429 should only block through proxies.
    • A 429 through proxies blocks the proxy only while 429 is in block_on. Who is affected: a policy whose block_on leaves 429 out (it blocked the proxy whatever blacklist_on said). What to do: add 429 to block_on to leave the proxy out on a 429; without it a 429 is a retryable status, retried after the backoff through the next proxy.
    • Unexpected HTML (a 2xx response with an HTML page where an image, XML, JSON or a manifest was expected) is a failed attempt on both paths: it counts, is retried after the backoff, is traced 200-html, and after the last attempt the fetch fails with linecaster.net.http.UnexpectedHTML (through proxies as MaxRetriesExceeded's cause), which names the expected format and the content type. HTML is told by the body's first bytes (after a byte order mark, whitespace and comments): an HTML document, whatever its label; under text/html also an HTML element, plain text or nothing. Data a server mislabels as text/html (JSON, XML with or without a declaration, an image) still passes, in ResourceReader too. Before, through proxies it blocked the proxy for an hour without using up an attempt; on a direct connection an image failed at once as an unreadable image and a resource failed at once. ManifestReader now says what it expects too (the manifest, the page images, ALTO files), so an HTML page there is retried and fails as UnexpectedHTML instead of passing as a manifest or image that does not parse. Who is affected: runs whose hosts answer a block or a soft 404 with HTML and 200. What to do: for a host whose HTML pages are a block (a CDN's challenge), block_on: [429, html] at that host leaves the proxy out again (direct: the worker pauses); stop_on: [html] stops the run as before; max_retries: 0 fails such a page after one attempt.
    • A block without Retry-After lasts 60 s at first and twice as long on each repeat (for that host, and through proxies for that proxy, until a successful response there; linecaster.net.http.block_wait), at most the host's block_ttl through proxies (default 3600 s) and max_pause direct (default 6 h). Before, a blocked proxy was left out for blacklist_ttl (3600 s) at once, and a direct pause doubled from 60 s up to an hour. With Retry-After nothing changes. Who is affected: runs through proxies whose hosts send 429s without Retry-After (their proxies come back sooner and are retried there), and direct runs with long pauses (a single pause may now pass an hour). What to do: nothing to keep a polite run; no setting restores the flat hour through proxies, and block_ttl is the ceiling of the doubling (proxies: {block_ttl: 72h} for a host whose block lasts three days); max_pause bounds the pauses direct.
    • The doubling of a proxy's blocks (and of a broken proxy's time out) travels with the proxy through the broker: each mark records its last wait without Retry-After (last_wait) and is kept that long past its end (keep), so a worker that claims a released proxy continues the doubling (60, 120, 240 s across workers) instead of starting at 60 s; before, each worker kept its own and a proxy that changed hands started again. The doubling starts again after a successful response through the proxy from that host (its ended marks are deleted then), or when the next block comes more than the last wait after the last one ended (a quiet period; also on the direct path, per host, linecaster.net.http.doubling). The broker's layout, file names and format (linecaster.broker/1) are unchanged. Who is affected: runs through proxies whose hosts block without Retry-After (their proxies stay out longer when they change hands), and workers of 0.4.0 and of this version sharing a broker: 0.4.0 reads the new marks' ends as before, ignores the new fields and deletes a mark at its end (the doubling then starts again), and this version reads 0.4.0's marks and starts their doubling at 60 s. linecaster broker clean keeps a mark during its keep (status no longer counts it expired); clean --marks removes it, and the doubling starts again. What to do: nothing; proxies: {block_ttl: ...} remains the ceiling.
    • A broken proxy (a proxy error, no connection to it) is left out after 3 such errors in a row (broken_after; it was 1), first for 300 s (broken_ttl; it was 3600 s), doubling each time it breaks again before it carries an answer, at most block_ttl. Who is affected: runs through proxy lists with unreliable proxies (each costs up to three attempts before it is left out, and comes back sooner). What to do: proxies: {broken_after: 1, broken_ttl: 3600} restores leaving it out at its first error for an hour.
    • max_pause is one count on both paths, per worker and host (http, linecaster.net.http.PauseTotal): the time the worker's requests to the host have waited since the host's last successful response, direct in pauses, through proxies for a usable proxy; once the next wait would pass it, the run stops (StopRequests). Before, through proxies it limited each wait for a proxy alone and started again whenever one became usable, so a host that turned every proxy away over and over (a page that is always HTML under block_on: [429, html]) never ended the run. Who is affected: runs through proxies whose hosts block again and again without a successful response: they now stop after max_pause of waiting. What to do: raise max_pause for a host whose blocks may last longer in all (hosts: {images.example.org: {max_pause: 24h}}).
    • On the direct path a block pauses only the requests to the host that sent it (Pause per host, HTTPFetcher.pause_for(host), HTTPFetcher.pauses()); before, it paused every request of the fetcher, whichever host it went to (one fetcher serves every host without an HTTP policy, e.g. a manifest server and an image server). Who is affected: runs whose readers fetch from several hosts directly; code that used HTTPFetcher.pause (gone). What to do: nothing for runs; code uses pause_for(host).

    • The HTTP settings of a reader (http) and of HTTPFetcher are renamed with the policy: proxy_blacklist_threshold is broken_after, proxy_blacklist_ttl is block_ttl, proxy_blacklist_on and pause_on are block_on (which includes 429 by default rather than adding to it), proxies_per_worker is per_worker, pause_wait is first_wait, and pause_max_wait is gone (the doubling stops at max_pause); broken_ttl is new; stop_on and block_on take html. In linecaster.net.http, PAUSE_ON, PAUSE_FIRST_WAIT, PROXY_BLACKLIST_THRESHOLD and PROXY_BLACKLIST_TTL are BLOCK_ON, BLOCK_FIRST_WAIT, BROKEN_AFTER (3) and BLOCK_TTL, with BROKEN_TTL new; PAUSE_MAX_WAIT and ProxyBlocked are gone; Pause takes first_wait and max_total (no max_wait); pause_left() gives what began the pause in words (HTTP 429, an HTML page) instead of the status; ProxyPool.block takes the Retry-After seconds or None (the doubling) with cap and first, ProxyPool.broken takes after, first and cap; each is now note_block/note_broken (in memory, at once: the fetcher calls them on its event loop) followed by publish (the broker's mark and release, which the fetcher runs in a thread). HTTPPolicy.stops_on_html is gone (the fetcher stops on html itself), and HTTPPolicy.describe() takes no options (the run's options are the policy's base) and states every rule that holds per host and path, defaults and opt-ins alike. Who is affected: code that builds fetchers or readers with these settings, or uses these names. What to do: rename as above; http={"broken_after": 1, "broken_ttl": 3600} and http={"block_on": [429, "html"]} restore the earlier proxy behavior.

    • --http-policy holds for every input fetched over http(s): --manifests (the manifests, their images and OCR files) and --pages (the images it fetches again) take it too, as --items and --parquet did (ManifestReader(http_policy=...), PageRecordReader(http_policy=...); every reader goes through linecaster.net.policy.Fetchers, one fetcher per host's settings). Who is affected: runs with --manifests or --pages and a policy (refused at startup before) and their workers (with proxies in the policy, the default worker count follows them, as for the other inputs); ManifestReader now has one fetcher per host's settings and takes a random User-Agent per task and fetcher. The recipe item-texts@1's expanded pipeline gains http_policy: null (a catalog migration; its behavior is unchanged). What to do: nothing; a derivative that pinned the old pipeline hash of item-texts@1 reads the new one from the lock.

Without --reuse their pages are fetched again and the files overwritten. The flag changes the pipeline's hash: a resume into an OUT of an earlier launch needs --new-pipeline.
    • How many proxies of a list a worker holds is the new HTTP-policy key proxies_per_worker (per host or at the root; also HTTPFetcher's and ProxyPool's parameter): share (the default) a fair share of the free ones, rebalanced as before, except that a worker claims at most 2 when it looks for proxies and grows to its share only by rebalancing, so the first workers no longer take the proxies of those still starting; 1 one proxy per worker, which sends every request through it and, when it is blocked or broken, releases it and claims another free one at once (useful with output on local disk or few proxies, with a worker per proxy); or a whole number N, up to N per worker, claimed one by one. Hosts that use one proxy list must set the same value. The default was 1 on main for a few hours and is share again: with one proxy per worker, using 250 proxies took 250 workers, and 250 workers writing to object storage hung in their listings of OUT/images (below); a run that wants one proxy per worker sets proxies_per_worker: 1.

With OUT on object storage (any fsspec protocol but a local one: s3://, gs://, hf://, az://, ...) the count stops at 64 (linecaster.runtime.run.OBJECT_STORAGE_WORKERS) in both modes: in one setup 250 workers writing to S3-compatible object storage hung where 64 ran cleanly. Give --workers for another count. The run states the count and why (250 proxies available, OUT on object storage → 64 workers, a fair share each). A host with rate limits and no proxy list keeps one worker; HF Jobs keep their rule (a worker is a Job).
    • linecaster.runtime.local.LocalExecutor's note may be a list of lines; linecaster.runtime.run.rate_note counts the proxies in use (1 of 2 proxies in use (1 proxy per worker)) when the workers hold fewer than the list.
    • A worker process no longer claims the lowest free worker slot of its machine: it takes a handed-over slot first, then the k-th free slot (one without a valid slot lease claimed more than a minute before, so a stopped run's slots are passed over and its peers' are not), k its executor's worker index (linecaster.broker.set_worker_index, set by LocalExecutor, RayExecutor and JobsExecutor; else random), and probes upward from there, so slot numbers no longer say in which order the processes came. Code that starts brokers itself and expects <machine>-0 first passes Broker(..., worker_index=(0, 1)).
    • A broker's renew logs a lost claim race (two claims at once both believed they won) at INFO, worker X lost a claim race for proxies/<id> to Y; it takes another; the WARNING ... lease on proxies/<id> expired (no renew within the lease time); it gives it up is only for a lease that really expired (its file gone or older than the lease time), which the worker now also gives up when nobody else has claimed the resource.
    • Proxies are shared through the broker (linecaster.broker, broker): --proxy-blocks FOLDER and an HTTP policy's root key proxy_blocks are gone; use --broker PATH and the root key broker (default OUT/logs/broker; runs pointed at one path share the proxies and their blocks). The old folder of block markers is not read; blocks found before are found again at the first request through each proxy. There is no alias.
    • With a proxy list the rate limits (--rate-limit, an HTTP policy's rate_limits for a host through proxies) hold per proxy, not per worker: each proxy is used by one worker at a time, which spaces its requests through the proxy by the strictest limit. A server sees up to the proxies times the limits, whatever the worker count, so a limit meant for all proxies together is now too high by the proxy count: give the limit one IP may send. Direct connections keep the limits per worker.
    • A host whose proxies are all blocked (or broken) no longer stops the run at once: its requests wait until a block ends or another worker gives a proxy back, up to the host's max_pause (6 h by default), and stop the run only when the first block ends later than that. A 429's Retry-After sets how long its proxy is blocked at the host, also when it is longer than blacklist_ttl (it was capped there).
    • The extra resilient-httpx is gone: a proxy list needs only linecaster[pybookget]. Scripts that list linecaster[...,resilient-httpx] drop it (pipelines/harvest.py does), or their install fails on the unknown extra. HTTPFetcher.proxies_in_rotation() and linecaster.net.http.proxy_rotation() are HTTPFetcher.proxy_counts() and proxy_counts() (held, blocked, free); HTTPFetcher's proxy_blocks and default_proxy_blocks are broker and default_broker; a request through proxies that used up its attempts raises linecaster.net.http.MaxRetriesExceeded (was resilient-httpx's, of the same name).
    • A 429 pauses the worker that got it instead of stopping the run or failing the page: an HTTP policy has a new per-host key pause_on (statuses that pause the worker's requests to the host until the response's Retry-After has passed, then retry the request; default [429]) and max_pause (default 6 h in all since the host's last successful response; beyond it the run stops). A policy with 429 in stop_on is refused (429 both in stop_on and pause_on): move it to pause_on (catalog.example.org: {direct: true, stop_on: [429, html]} becomes {direct: true, pause_on: [429], stop_on: [html]}), or keep it in stop_on with pause_on: [] to still stop the run on it; there is no alias. Without a policy the default applies as well: on a direct connection a 429 used to be retried per request by pybookget (each retry after the longer of its backoff and the Retry-After, at most 300 s, up to max_retries), the other requests going on meanwhile, and the page or resource failed with HTTPStatusError once its retries were used up; now the worker's requests to the host wait out the Retry-After (a minute doubling to an hour without one), the request is tried again without using up a retry, and the page does not fail. http={"pause_on": []} keeps the old behavior. Through a proxy list nothing changes: a 429 leaves that proxy out.
    • max_retries (http={"max_retries": ...}, an HTTP policy's) counts retries after the first attempt, as its name says, where it counted attempts: max_retries: n now makes n + 1 attempts, and 0 is a single attempt. The default is 4 (still 5 attempts). A setting written for the old meaning gets one attempt more; lower it by one to keep the old count. linecaster pins pybookget 1.2.0 (45814da), which counts this way too.
    • pp-doclayout-plus-l without an edition resolves to edition 2, which orders the regions with XY-Cut++ instead of plain XY-cut. A run that must keep the old order names pp-doclayout-plus-l@1.
    • pipeline_sha256 leaves an in-process engine's endpoint and timeout options out (ENGINE_OPERATIONAL: where its service is). A derivative's run whose engine has an option of either name gets another hash: a resume into its folder needs --new-pipeline. No released recipe is affected.
    • linecaster.testing.check_engine calls a page engine (recognition, unit page) with an empty transcription (no regions, no lines), not the sample layout's regions.
    • --rate-limit holds per worker (process), not per task: the tasks a worker runs one after the other share one fetcher and its limits (HTTPFetcher.shared), where each task started its limits afresh. A server sees the workers running at once times the limits, as before; the run now states it before it starts (run.rate_note).
    • --tasks and --workers default to an automatic choice (linecaster.runtime.run.allocate): a pipeline without engines (pipelines/harvest.py) runs tasks of about 1,000 pages (or 5 items) from its input, one worker with --rate-limit, one per CPU without; a pipeline with engines keeps one task, every task at once. Resuming a run started with the old default (--tasks 1) needs --tasks 1.
    • http(s) requests have a deadline per attempt (HTTP_DEFAULTS: pybookget's attempt_timeout=15 and attempt_min_rate=50_000, i.e. 15 s plus 1 s per 50 kB of Content-Length, counted after the rate limits): an attempt past it is cut and retried. A server that needs longer for a response without Content-Length needs http={"attempt_timeout": None} (or a longer one). linecaster pins pybookget bf8eee1, which has the setting.
    • --prefetch and the readers' prefetch= argument are gone: ManifestReader and ImageParquetReader request http(s):// pages ahead in a window that sizes itself; drop the option. linecaster.net.prefetched takes (entries, submit, cancel, future=, fetcher=).
    • ImageParquetReader and ManifestReader item tables divide rows, not files, over the tasks; ImageParquetReader no longer splits a task's rows by datatrove's ParquetReader.read_files_shard, so limit and skip apply before anything is fetched, and no Parquet file is a PipelineConfigError (was datatrove's RuntimeError). A table no longer needs splitting into one file per task.

    • The run record's schema is linecaster.run-record/1 (was linecaster.run/1): pipeline lists the stages with every block's to_dict() and contract (was a list of block entries; the separate stages is gone), and pipeline_sha256 is new. A run into an OUT whose record has another pipeline_sha256 (or none: a record from before) is refused unless --new-pipeline; another --tasks always is.
    • Page records carry schema: linecaster.page/1 in their row. Records without one (written before phase 1) are read with ocr as ocr_new, and a pages/ folder without records is read from its sibling rows/: no transcription="ocr" needed any more.
    • Engines load in warm_up() before the first page, not on it: a page's measured seconds no longer include loading; the load time is the block's warm_up_seconds stat. ModelServer and ChatModelServer start their servers in warm_up() (stat warm_up_seconds, was the boot time stat).
    • engine_spec(ref) and preset_models(models) take installed=True; tests that replace engine_spec accept it.
    • On HF Jobs the tasks log JSON lines (LINECASTER_LOG_JSON=1, runtime.jobs.JobsExecutor; the run record's executor is JobsExecutor).
    • Every run is traced (OpenTelemetry, a new required dependency: opentelemetry-api, -sdk, -exporter-otlp-proto-http): OUT/traces/ appears in every run folder, and a sampled page's record carries metadata.trace_id.     • Observers: on_task_end(error=None) (was on_task_end(); an own observer adds the parameter), and new hooks on_task_event, on_leave, environment(). Stream blocks notify request (with a carrier) after prepare, and done with tokens and finish_reason; PageRecognizer notifies prepare once (was twice).

    Fixed¶

    • PageRecordReader(fetch_images=True), ImageFetcher and ImageConverter dropped the fragment of page.image.uri and fetched the whole file: for a PdfReader page (file.pdf#page=n) the PDF, for an ImageParquetReader row with embedded bytes the Parquet file. A PDF page is now rendered as PdfReader renders it (at the record's metadata["pdf"]["dpi"]), a Parquet row's image read (columns id and image), and any other fragment is the page's error (field image), never the wrong bytes (linecaster.blocks.readers.fragments).
    • ImageConverter without keep_bytes declared only metadata replaced although the page leaves without its image bytes: its contract now removes image, so the builder no longer treats the image as available after it.
    • ImageFilesWriter rewrites page.image.uri and extra (to name the copy) without declaring it: its contract now replaces metadata.
    • RegionRecognizer replaces the transcription's earlier lines but declared lines only as added: its contract now replaces lines and text, so it may follow a line step.
    • RegionRecognizer ignored an explicit pad when the adapter has a region_pad.
    • RegionRecognizer failed the task on a page without image bytes; the page now carries the error (found by check_block).

    • PageValidator(required=("image",)) declared that it reads the image bytes, although it checks the page record's image entry: a page field is now read as metadata, so the validator may follow an ImageConverter that removes the bytes.

    • PageParquetWriter writes a fixed schema: datatrove took a file's columns from its first row, so a page's errors were dropped when the first page of a file had none. Page records in Parquet now always have an errors column (null without errors).

    • Tracing holds no page documents: a page a block drops no longer stays in memory, with its image, until the task ends; its trace ends when the next page enters that block.
    • A sampled page's metadata.trace_id is derived from the run and the page id, so a rerun of a run writes the same page records.
    • runtime.jobs.dependencies() reads the pipeline script and its lock as they are at the commit the Jobs install, not as the checkout holds them (with a warning when the commit is not in the checkout).
