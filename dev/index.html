    Linecaster¶

    Modular OCR pipelines you can run anywhere¶

    An Intertype C4 linecaster (1961). Drawing after a photograph in the Science Museum Group Collection, CC BY-NC-SA 4.0. Credit

    Build an OCR pipeline from interchangeable parts: a model that reads the text, either a vision-language model or a line recognizer, combined with layout, table and formula models and post-processing. Run the same pipeline on a laptop, a GPU server, a cluster or Hugging Face Jobs.

    Docs: storytracer.github.io/linecaster (the newest release; this README, the reference, a page for every block and catalog entry, and llms.txt for coding agents).

    Jump to: Why · Quick start · How it works · Run anywhere · Outputs · Models and blocks · Reference · Versions

    🤔 Why Linecaster¶

    Turning a scan into usable text takes more than one model. The text has to be read, by a vision-language model or by a line recognizer. Around that, the layout has to be found, tables and formulas rebuilt, and the text cleaned, recomposed and written in the formats people use. Every model comes with its own software, and every machine has its own way of starting and scaling work. Swapping a model or moving to bigger hardware usually means starting over.

    Linecaster keeps the parts and the machines apart:

    • 🧩 Any step. Reading, layout, lines, tables, formulas and post-processing are separate steps. Use a vision-language model on whole pages or on layout regions, or a line recognizer with a line detector, and add any of the other steps.
    • 🌍 Any machine. Define the pipeline once. Only the line that starts the run changes.
    • 🖥️ No serving stack to build. Models load inside the pipeline, or each task starts its own model server on its GPU.
    • 🎯 The same result everywhere. A page's text depends only on that page, never on how many machines share the work.
    • 🔁 Built for long runs. Interrupted runs resume. Damaged pages are set aside with the reason.

    🚀 Quick start¶

    You need Python 3.12 and uv 0.13.6 or newer.

    git clone https://github.com/storytracer/linecaster
cd linecaster

    The quickest start is launch.py with a name: a recipe (a tested combination of models) or a model that reads whole pages. It knows which pipeline that needs. For your own combination, fill a pipeline's slots yourself, one preset per step. Either way you get a page record per page in out/pages, and --files adds ALTO, PAGE-XML, hOCR, text and Markdown.

    uv run launch.py squiddle scans/ out/          # a recipe
uv run launch.py lightonocr-2-1b scans/ out/   # a model
uv run launch.py                               # lists the recipes and models

    Every pipeline option works after the name, e.g. --on hf-jobs or --files out/files.

    Note

    Each pipeline is a self-contained uv script: a # /// script block at the top lists what it needs, with pinned versions, and a .lock file sits next to it. uv run installs it on the first run; the models download on first use.

    🍳 A recipe¶

    A recipe is a named combination: a pipeline, a preset edition for each step, and its options, with its own edition, provenance and evidence. SquiddleOCR's is squiddle:

    uv run launch.py squiddle scans/ out/

    Options after the name change single steps or settings; the run record lists them as overrides.

    🤖 A vision-language model reads each page¶

    Needs an NVIDIA GPU and the vllm command of vLLM on the PATH.

    uv run launch.py lightonocr-2-1b scans/ out/

    Any model for whole pages works. A region model reads each layout region instead, in the VLM pipeline with a layout preset: uv run pipelines/transcribe_vlm.py scans/ out/ --layout pp-doclayoutv3 --recognition minicpm-ocr-1.0.

    🧱 The modular pipeline: smaller models, step by step¶

    Layout, line detection and a line recognizer, then post-processing into a document. You pick each step's preset; linecaster models lists them.

    uv run pipelines/transcribe_modular.py scans/ out/ \
  --layout pp-doclayoutv3 \
  --lines pp-ocrv6-medium-det \
  --recognition kraken-ppocrv6-medium \
  --typography ratios --recomposition unicode-recomposition --composition docling-composition \
  --files out/files --formats md,alto

    --layout single-region reads the page as one region (no layout model); --tables and --formulas add those steps. The rule-based steps are slots too, each a preset: --typography (headings and their levels), --recomposition (running text in paragraphs; without it the page stays as laid out), --composition (the page's document, for Markdown, HTML and JSON) and --normalization (the readable item texts' normalization, with --item-texts); a recipe fills them all. --set recognition.batch_size=4 changes one option of a preset. --files writes any per-page format of PageFileWriter (--formats); --naming squiddleocr --furniture writes them as squiddleocr does.

    ✍️ Your own pipeline¶

    A pipeline is a list of blocks. This is the modular pipeline above, cut down:

    from datatrove.executor import LocalPipelineExecutor
from linecaster.backends import InProcess as P
from linecaster.blocks.composition import (
    Composer, Recomposer, Typographer)
from linecaster.blocks.layout import LayoutDetector
from linecaster.blocks.lines import (
    LineAssigner, LineDetector)
from linecaster.blocks.readers import ImageFolderReader
from linecaster.blocks.recognition import LineRecognizer
from linecaster.blocks.text import UnicodeNormalizer
from linecaster.blocks.writers import PageFileWriter

pipeline = [
    ImageFolderReader("scans/"),
    LayoutDetector(P("linecaster_paddlex:PaddleLayoutEngine")),
    LineDetector(P("linecaster_paddlex:PaddleLineEngine")),
    LineAssigner(),
    LineRecognizer(
        P("linecaster_kraken:KrakenRecognitionEngine")),
    UnicodeNormalizer(),
    Typographer("ratios@1"),
    Recomposer("unicode-recomposition@1"),
    Composer("docling-composition@1"),
    PageFileWriter("out/", formats=("md", "alto")),
]
LocalPipelineExecutor(
    pipeline, logging_dir="out/logs").run()

    Save it in pipelines/ with the # /// script block of pipelines/transcribe_modular.py at the top, which brings the engines, and uv run it. Built with linecaster.runtime.run.main, as the pipelines are, it gets their command line for every machine, and a check before anything starts: every block declares what it reads and adds, so a recognizer without lines or a writer after a server fails at once, with every problem listed. --dry-run prints the plan and its graph as a Mermaid flowchart; --until, --after and --tap-after run or tap a part of it. ModularTranscriber puts layout, lines, line assignment and line recognition together in one block (docs/reference/pipelines.md).

    Tip

    The two kinds mix: a LayoutDetector followed by RegionRecognizer has a vision-language model read each layout region, which is what pipelines/transcribe_vlm.py --layout … does.

    🧩 How it works¶

    Four ideas carry the design:

    1. 📋 One record per page. Every step reads the page's Transcription and adds its part: regions, lines, text, tables, a document. Steps never talk to each other, so any step can be replaced.
    2. 📐 Every block declares its contract: what it reads, adds, replaces or removes. A pipeline is checked before it starts, and its graph is drawn from the contracts; a recognizer without lines fails at once.
    3. 🔌 Each model step has a backend. InProcess loads the model inside the pipeline. Served sends pages to a model server and Chat to a vision-language model behind an OpenAI-compatible server, both through saturate, which keeps enough pages in flight that the GPU never waits.
    4. 🏗️ The executor decides where it runs. Pipelines are datatrove pipelines. Executors split the pages into tasks, run them locally, on a Ray cluster or on Hugging Face Jobs, and resume where a run stopped.

    🌍 Run it anywhere¶

    A pipeline runs on every machine with the same steps. Only its flags change:

    Where Flags
    💻 This machine none: the models load inside the pipeline
    🖥️ This machine, with a server --backend served
    🧮 A Ray cluster --on ray --tasks 64
    ☁️ Hugging Face Jobs --on hf-jobs --commit <sha>

    On Ray and HF Jobs every task gets one GPU and starts its own model server on it.

    📥 Where the pages come from

    The readers follow datatrove's conventions: files found by a glob or listed in a paths_file, distributed over the tasks in turn, with --limit and --skip per task. Any fsspec path works: local, s3://, hf://.

    Input Flags
    a folder of images IMAGES (--glob-pattern to choose files; --item-from-parent: the subfolder is the item)
    a list of images IMAGES --paths-file pages.txt (one image per line, relative to IMAGES)
    Parquet with an image column (pages) --parquet PATH (--id-key, --image-key, --item-key, --sequence-key)
    items' manifests (IIIF, METS) --manifests FOLDER, --manifests list.txt (one link per line), or an item table: --manifests items.parquet --manifest-key manifest_url [--item-key item_id]
    page records of an earlier run --pages OUT/pages (images fetched again from their URIs)
    PDF files the PdfReader block (extra pypdfium2): one item per PDF, each page rendered to a lossless WebP image; no pipeline flag yet
    • The image column can hold the bytes, a Hugging Face image struct ({bytes, path}), or a path: absolute, or relative to --image-folder. Without a page-id column, --item-key and --sequence-key name pages <item>_<0001>.
    • A Hub image dataset is just Parquet: --parquet hf://datasets/<repo>@<revision>/data.
    • A public bucket needs no credentials with FSSPEC_S3_ANON=true.
    • Manifests (the pybookget extra, which brings pybookget): a manifest lists an item's pages and their files, in order. Two formats are read, told apart by their content (or --manifest-format):
    • IIIF Presentation 2 and 3: images at full size through the image service (--iiif-format), the image's own URL after a 404.
    • METS with MODS, also inside an OAI-PMH GetRecord response (the DFG viewer's profile; Kitodo, Goobi, Visual Library): pages from the physical structure map in ORDER, images from the first file group of MAX, ORIGINAL, MASTER, DEFAULT (the next one after a 404). Relative file links are read next to the METS file, so a package with local files works too.
    • Each manifest is one item: one reader entry (or one row of an item table), so an item's pages stay in one task. Every page with an image becomes <item>_<0001>. The item id comes from --item-key, else from the manifest link's last segment that isn't manifest/mets; --item-id-pattern overrides it.
    • Each page record keeps the item's and the page's data in metadata.manifest: format, link, id, label, rights, identifiers, descriptive metadata (MODS creators, date, language, …), the page's own id and label. An item table's other columns go into each of its pages' metadata.
    • --existing-ocr also fetches the library's own OCR the manifest links (METS FULLTEXT, IIIF seeAlso/rendering; ALTO or hOCR), and a TranscriptionConverter keeps it as the transcription ocr_original, next to the new one.
    • An entry may be a IIIF Collection: its manifests are read as items (one level so far).
    • http(s):// image URLs (manifests, or paths in a Parquet column) go through pybookget:
    • retries that honor Retry-After, and an honest user agent;
    • the environment's proxy settings (HTTPS_PROXY, HTTP_PROXY, ALL_PROXY, NO_PROXY), as everywhere else in Linecaster;
    • --rate-limit 5/1 (repeatable) per task, so the server sees up to --workers times that.
    • Harvest, transcribe, bind. Harvesting first is the usual path, and it keeps the GPUs off the network:
    • uv run pipelines/harvest.py --manifests items.parquet --manifest-key manifest_url OUT --tasks 16 --workers 4 --rate-limit 5/1 --existing-ocr writes OUT/images/<item>/<page>.<ext>, OUT/ocr/…, the manifests as fetched in OUT/manifests/, and page records;
    • uv run pipelines/transcribe_modular.py --pages OUT/pages OUT2 ... (or transcribe_vlm.py) keeps all of it and adds the new transcription; OUT/images --item-from-parent reads the plain folder instead;
    • uv run pipelines/bind.py OUT2/pages OUT3 --recipe item-texts binds each item (below).
    • For small runs, --manifests also works directly in the transcribe pipelines.
    • Item-level outputs (per book, issue or manuscript): pipelines/bind.py binds each item's pages into one, recomposes it as one (paragraphs continued across page breaks), normalizes it and composes the item's document, each step a preset (--recomposition, --normalization, --composition; the recipe item-texts fills them). It writes:
    • OUT2/texts/<variant>/<rank>.jsonl.gz, one row per item and text variant (--files also OUT2/texts/<variant>/<item>.txt|.md; --variants picks them; --no-texts);
    • OUT2/documents/<format>/<item>.<ext>, the item document in md, txt and json (--formats adds html and doclang; --furniture, --dividers; --no-documents).
    • With several tasks, an item's pages can land in different tasks: the first run writes its page records into item shards (--item-shards 64: OUT/pages/<shard>/<rank>.jsonl.gz, every item in one shard), and bind.py reads whole shards, one or more per task.
    • --item-texts DIR in a transcribe run does the same for the texts in a second stage of that run.
    🖥️ A model server that stays up

    serve starts linecaster serve with the presets you name and keeps them loaded; --endpoint points runs at it:

    P="--layout pp-doclayoutv3
   --lines pp-ocrv6-medium-det
   --recognition kraken-ppocrv6-medium"
uv run pipelines/transcribe_modular.py serve $P
uv run pipelines/transcribe_modular.py scans/ out/ $P \
  --endpoint http://127.0.0.1:8100/v1

    For a vision-language model, --recognition-endpoint points pipelines/transcribe_vlm.py at a running vLLM or SGLang. The servers listen on loopback only.

    🧮 On every GPU, with Ray

    ray runs Ray's own command line with the pipeline's packages, so every machine has the same Ray and Linecaster ($P: the presets, as above):

    R=pipelines/transcribe_modular.py
uv run $R ray start --head --num-gpus 8
# on each other machine:
# uv run $R ray start --address=<head>:6379
uv run $R scans/ out/ $P --on ray --tasks 64

    Images and output must be on storage every machine can reach.

    ☁️ On Hugging Face Jobs

    One GPU per Job. Each Job installs Linecaster at a pushed commit, with the engines, sources and pins of the pipeline's # /// script block:

    uv run pipelines/transcribe_modular.py \
  s3://bhl-open-data/images \
  hf://buckets/<ns>/<bucket>/<run> $P \
  --paths-file hf://buckets/<ns>/<bucket>/pages.txt \
  --on hf-jobs --commit <sha> \
  --tasks 4000 --workers 64 --item-shards 64 \
  --env FSSPEC_S3_ANON=true
    • Tasks and workers: datatrove hands out the pages over the tasks in turn, and --workers Jobs run at the same time; the next starts when one finishes.
    • A rerun into the same output runs only the tasks that didn't finish.
    • --tasks-per-job (datatrove's) lets a single-GPU Job run several tasks one after the other; each task starts its own model server.
    • Multi-GPU Jobs: --flavor l4x4 --gpus 4 runs four tasks per Job, one per GPU. pipelines/transcribe_vlm.py picks the server image its model was checked with; --image names another. --dry-run prints the plan and launches nothing.
    🧱 What the flags do, for your own pipeline
    • Backends: InProcess("module:Class", **kwargs) loads a model inside the pipeline; Served(endpoint, name) sends pages to a server through saturate; Chat(preset, endpoint) sends them (or their regions) to a vision-language model behind an OpenAI-compatible server, for PageRecognizer and RegionRecognizer.
    • Server blocks start a server inside each task and go last in the pipeline, so the server lives until every page is written: ChatModelServer(spec) starts vLLM or SGLang, ModelServer(MODELS, script=...) a pipeline's serve.
    • Executors: LocalPipelineExecutor, RayGPUExecutor, and on HF Jobs JobsExecutor (datatrove's JobsPipelineExecutor, logging JSON lines) or GPUJobsExecutor with dependencies(commit, script), which turns a script's # /// script block into what each Job installs.

    MODELS names the models a server hosts:

    MODELS = [
    {"name": "layout",
     "spec": "linecaster_paddlex:PaddleLayoutEngine"},
    {"name": "recognition",
     "spec": "linecaster_kraken:KrakenRecognitionEngine",
     "kwargs": {"model": "medium"}},
]

    linecaster.runtime.run puts these together for the pipelines.

    📦 What you get¶

    Output What it is for
    📜 Text as printed checking against a hand-made transcription
    📖 Readable text reading and training: old letterforms folded, hyphens joined, paragraphs flowed
    📝 Markdown, HTML, DocLang, Docling JSON documents with headings, tables and formulas
    🏛️ ALTO, PAGE-XML, hOCR libraries and viewers: every word with its position
    🗂️ Page records (JSON Lines, Parquet) later pipelines: every intermediate result

    Files come per page or, for an item, one per text variant. Word positions need a model that gives them, such as a line recognizer.

    Every run is also traced with OpenTelemetry: each task, and one page in a hundred (chosen by page id, so the same ones every time) plus every page that failed, block by block and into the servers. The traces land in OUT/traces/, and in your own tracing backend when the standard OTEL_* variables point to one; nothing is sent anywhere else. linecaster traces OUT says where the time went: per block the time per page, for served blocks how much of it was the queue and how much the model, the slowest pages, and each task's warm-up (--trace-sample 1 traces every page; docs/reference/tracing.md).

    🧰 Models and blocks¶

    Every configuration is a preset in Linecaster's catalog: one engine, one model at a pinned revision, and its settings. The original model card is copied next to it, unchanged, at exactly that revision. linecaster models lists the presets; docs/catalog has a page for each engine, model, preset, pipeline and recipe, with the results and where every number comes from.

    Vision-language models run behind vLLM or SGLang. The other models run inside the pipeline or behind linecaster serve, one package per engine: linecaster-kraken (kraken), linecaster-paddlex (PaddleX) and linecaster-tesseract (Tesseract).

    🔩 Blocks¶

    A pipeline is a list of blocks, one role each. Model blocks take a preset or a backend; the rule-based blocks take a preset of a built-in engine (e.g. Typographer("ratios@1")), the UnicodeNormalizer none. docs/blocks has a page for each block: its contract, backends, options and where it comes in a pipeline.

    Family Block What it does
    Readers ImageFolderReader Reads one page per image file of a folder or bucket.
    Readers ImageParquetReader Reads one page per row of Parquet files with an image column.
    Readers ManifestReader Reads one page per image of each item's manifest: IIIF Presentation 2 or 3, or METS with MODS (also inside an OAI-PMH response).
    Readers PageRecordReader Reads the page records an earlier run wrote (JSON Lines or Parquet), so a pipeline can add one more part.
    Readers PdfReader Reads one item per PDF file, one page per PDF page in order, each rendered to a lossless WebP image.
    Layout LayoutDetector Detects the layout regions of every page, with their labels and reading order, by a layout engine.
    Lines LineAssigner Assigns the lines detected on the whole page to the layout regions and orders them row by row.
    Lines LineDetector Detects the text lines of every page, with their geometry, by a line detection engine.
    Recognition FormulaRecognizer Recognizes every formula region as LaTeX by a formula engine.
    Recognition LineRecognizer Recognizes the text of every line by a line recognition engine.
    Recognition PageRecognizer Recognizes every page with a chat VLM, whose completion becomes the page's transcription.
    Recognition RegionRecognizer Recognizes each layout region of every page with a chat VLM, one request per region crop.
    Recognition TableRecognizer Recognizes the structure of every table region by a table engine.
    Conversion ImageConverter Converts each page's delivered image into the working image with an image engine and writes it.
    Conversion ImageFetcher Loads each page's image again from its address, for the blocks that need pixels.
    Conversion TranscriptionConverter Reads the transcription file that comes with each page (ALTO, PAGE-XML, hOCR or plain text) into a named transcription.
    Text CharacterNormalizer Normalizes the texts of every line, paragraph and table cell by a normalization engine, next to the text as written.
    Text UnicodeNormalizer Normalizes the as-written text of every line and word to one Unicode normalization form, NFC by default.
    Composition Composer Composes the DoclingDocument of a page or an item by a composition engine.
    Composition Recomposer Recomposes the running text of a page or an item into paragraphs by a recomposition engine.
    Composition Typographer Determines the typographic hierarchy of every page by a typography engine.
    Binding Binder Binds each item's page records, in order, into one item record.
    Binding Splitter Splits each item record into its page records again, in the item's order, with what the item-level blocks added.
    Validation PageValidator Marks the page records that do not validate against Page or lack a required part with an error each.
    Validation RecipeStamper Stamps the recipe edition a run follows on every step of every transcription, of a page or of each page of an item record.
    Servers ChatModelServer Starts a chat VLM server (vLLM or SGLang) inside the task for its Chat backends, through saturate's Engine.
    Servers ModelServer Starts linecaster serve inside the task for its served model blocks, through saturate's Engine.
    Writers ImageFilesWriter Writes each page's image bytes as they came, one file per page.
    Writers ItemDocumentWriter Writes the document of each item record, one file per format: Markdown, text, HTML, DocLang, JSON.
    Writers ItemTextWriter Writes the text variants of each item record as JSON Lines or as files.
    Writers PageFileWriter Writes one file per page and format: ALTO, PAGE-XML, hOCR, text, Markdown, HTML, DocLang, JSON and more.
    Writers PageJsonlWriter Writes the page records as JSON Lines, one file per task, or into item shards for a later stage.
    Writers PageParquetWriter Writes the page records as Parquet, one file per task.
    Writers RejectWriter Writes every page that carries errors to the task's rejects file and passes every page on.
    Composites ModularTranscriber Reads a page's lines the modular way: layout, lines on the whole page, line assignment, line recognition.

    📚 Reference¶

    📋 The data model
    Class Holds
    Item a book, issue, manuscript or file
    Page one page: its image and named transcriptions
    Transcription regions, lines and words with positions, reading order and confidences, plus a DoclingDocument
    Text a whole item's text in one text variant (below)
    • A page can hold several transcriptions side by side, for example the delivered OCR, a new one and the ground truth.
    • Positions are pixels of the page image; boxes are [x, y, width, height].
    • A Transcription survives a round trip through JSON exactly, and through ALTO, PAGE-XML and hOCR without losing structure, text, positions or confidences.
    • docs/reference/data-model.md and docs/reference/serialization.md are the reference.
    📖 Text variants

    Text moves along three independent dimensions, one step at a time:

    Dimension From To
    Characters as written normalized, expanded, regularized
    Flow as laid out flowed
    Scope full page body text only

    Named variants:

    • verbatim_txt: as written, as laid out, full page.
    • readable_txt, readable_md: normalized characters, flowed paragraphs, hyphens joined, body text; made from the item's recomposition, so a paragraph runs on across a page break.

    All text is Unicode NFC. Normalization folds long s, ligatures and r rotunda; it keeps æ, œ, ø and ß. Spelling is never modernized.

    🎯 Why results are the same everywhere
    • Models batch only the lines of one page, in a fixed order. Pages are never mixed.
    • Model revisions are pinned. Numerically relevant library versions are pinned in each pipeline script.
    • So a page's output depends on the page and the models, not on the machine, the number of GPUs or what else is running.
    • Different GPU types can still differ in the last digits of their arithmetic, which causes rare one-character differences.
    🔁 Long runs in stages
    • Each stage reads the page records the last one wrote (PageRecordReader), adds one part and writes complete page records again.
    • Originals are never changed.
    • A page that fails a check or a step carries the reason; the RejectWriter writes it to rejects/, later model steps pass it by, and too many failures fail the task.
    • datatrove keeps logs and completion markers in logs/, so finished tasks are skipped on a rerun.
    🧭 Design principles
    • Every step is replaceable. Steps share a data model and nothing else.
    • Deployment is not part of the pipeline. Executors and backends change; steps do not.
    • The text as written is kept. Readable variants are derived from it and stored next to it.
    • The core stays light. No machine-learning libraries in the core; engines are separate packages that a pipeline installs when it needs them.
    • Readers stay generic. Folders, buckets, Hugging Face datasets, and the standards for manifests (IIIF, METS/MODS). Adapters for one collection or institution belong in the projects that use Linecaster.
    • Open formats out. ALTO, PAGE-XML, hOCR, text, Markdown, HTML, DocLang, DoclingDocument.
    📚 The catalog
    • One catalog, in src/linecaster/catalog/data/: models (models/<id>/model.yaml, with the upstream card in upstream/<revision>/), presets by step (presets/<step>/<id>.yaml), recipes (recipes/<id>.yaml) and evidence records (evidence/*.yaml). The data is YAML, checked against JSON Schemas generated from the code (src/linecaster/catalog/schemas/); the reasons are in a Markdown file next to it (<id>.md, model.md).
    • Code has versioned ids. A preset names its engine (engine: kraken.recognition.v1), a recipe its pipeline (pipeline: transcribe_modular.v1). An incompatible change of options is a new id (.v2).
    • Versions: version and revision are upstream's, verbatim and exact. A preset or recipe has its own integer edition, referred to as id@edition.
    • Released editions don't change. catalog.lock keeps each released edition's functional content and its hash, and linecaster catalog verify fails when a released edition changes. Old editions stay resolvable.
    • Provenance: each page file names the presets and revisions that made it (ALTO Processing, PAGE-XML MetadataItem, hOCR metas). Each run writes OUT/run.yaml with every block's parameters, preset, edition, hash and override, and the pipeline's hash; a run into a folder of another pipeline is refused.
    • Recipes (recipes/<id>.yaml): a pipeline, a preset edition per slot, options. A recipe's hash covers its presets' hashes, so one recipe edition pins everything down to the weights.
    • Evidence records name their source: a Linecaster run, the BHL board, a model card's claim. A whole pipeline's results belong to a recipe; a preset's to the preset, with the rest of the pipeline as context.
    • docs/reference/catalog.md is the full reference.
    🛠️ Extending Linecaster
    To add Write
    a model linecaster catalog pin <id> --hf <repo> for its model entry and card, then a preset (presets/<step>/<id>.yaml, its reasons in <id>.md) and linecaster catalog release <id>
    a vision-language model the same, with engine: chat.v1 and an adapter in linecaster.adapters.ADAPTERS if no existing one fits
    an engine a class with engine_id, step, Options, capabilities, load() and __call__(image, transcription), packaged under engines/ and registered as an entry point (linecaster.engines); it imports only linecaster.data and linecaster.engines.api, and linecaster.testing.check_engine tests it
    a recipe recipes/<id>.yaml: a pipeline id, a preset edition per slot, options; then linecaster catalog release <id>
    a processing step a PageBlock with process_page(doc, page) and its contract(), a docstring to the standard, tested with linecaster.testing.check_block; uv run linecaster docs then writes its page

    An engine runs both inside the pipeline and behind linecaster serve without further work.

    🧪 Tests and checks
    Check Command
    the core's tests uv run pytest (tests marked gpu or network skip where the device or the network is missing)
    an engine package's tests uv run tests/test_engines_catalog.py engines/<engine>/tests (in the engines' environment)
    the docs are current uv run linecaster docs --check
    released catalog editions are unchanged uv run linecaster catalog verify
    the docs site builds uv run --group docs mkdocs build --strict
    the squiddle recipe against its goldens tests/parity/compare_goldens.py RUN GOLDENS (on a machine that has them)

    The CI workflow runs the first one without the engines, and the three after it, on every push and pull request. linecaster.testing gives engine packages and the projects built on Linecaster the same tools: sample pages, fake CPU engines, a fake chat server, and the conformance checks check_engine and check_block.

    🏷️ Versions and changes¶

    The current release is v0.1.0. CHANGELOG.md lists every release's changes, upgrade notes first. While the version is 0.x, a release may break things without a deprecation period; what counts as breaking is in docs/reference/compatibility.md. Released catalog editions never change, so a run record made with an older release still resolves. The docs site keeps one version per release, latest the newest, and dev for main.
