    Linecaster¶

    Modular OCR pipelines you can run anywhere¶

    An Intertype C4 linecaster (1961), after a photograph in the Science Museum Group Collection, CC BY-NC-SA 4.0. Credit

    Linecaster turns page images into text. You build an OCR pipeline from interchangeable steps (a model that reads the text, layout, tables, formulas, post-processing) and run it unchanged on a laptop, a GPU server, a Ray cluster or Hugging Face Jobs.

    • 🧩 Any step is replaceable. A vision-language model or a line recognizer reads the text; layout, table and formula models and rule-based post-processing are separate steps.
    • 🌍 Any machine. Only the command line changes, never the pipeline.
    • 🎯 The same result everywhere. A page's text depends only on that page and the pinned models.
    • 🔁 Built for long runs. Interrupted runs resume; failed pages are set aside with the reason.

    📖 Docs: storytracer.github.io/linecaster: the reference, a page for every block and catalog entry, and llms.txt for coding agents.

    🚀 Quick start¶

    You need Python 3.12 and uv 0.13.6 or newer.

    git clone https://github.com/storytracer/linecaster
cd linecaster
uv run launch.py                               # list the recipes and models
uv run launch.py squiddle scans/ out/          # run a recipe
uv run launch.py lightonocr-2-1b scans/ out/   # run a vision-language model (needs vLLM and a GPU)

    You get one page record per page in out/pages/. Add --files out/files --formats md,alto for per-page files.

    Note

    Every pipeline is a self-contained uv script with pinned dependencies and a lock file next to it. uv run installs what it needs on the first run; models download on first use.

    🧭 Three ways to transcribe¶

    1. A recipe: a tested combination of presets, one per step, with its own edition and evidence.

    uv run launch.py squiddle scans/ out/

    2. A vision-language model reads each page, or each layout region. It runs behind vLLM or SGLang, so it needs an NVIDIA GPU and the vllm command on the PATH.

    uv run launch.py lightonocr-2-1b scans/ out/
uv run pipelines/transcribe_vlm.py scans/ out/ --layout pp-doclayoutv3 --recognition minicpm-ocr-1.0

    3. The modular pipeline: layout, lines and a line recognizer, then post-processing. You choose a preset for every step; linecaster models lists them.

    uv run pipelines/transcribe_modular.py scans/ out/ \
  --layout pp-doclayoutv3 \
  --lines pp-ocrv6-medium-det \
  --recognition kraken-ppocrv6-medium \
  --typography ratios --recomposition unicode-recomposition --composition docling-composition
    Flag Effect
    --layout single-region the whole page as one region, no layout model
    --tables, --formulas add table and formula recognition
    --typography headings and their levels
    --recomposition running text in paragraphs (without it, the page stays as laid out)
    --composition the page's document, for Markdown, HTML and JSON
    --set recognition.batch_size=4 change one option of a preset
    --files DIR --formats md,alto per-page files: ALTO, PAGE-XML, hOCR, text, Markdown, HTML, DocLang, JSON
    --dry-run print the plan and its graph, run nothing

    Options after a recipe's name override single steps; the run record lists them.

    📥 Input¶

    Pages from Flags
    a folder of images IMAGES (--item-from-parent: each subfolder is an item)
    a list of images IMAGES --paths-file pages.txt
    Parquet with an image column --parquet PATH (--image-key, --item-key, --sequence-key)
    IIIF or METS manifests --manifests FOLDER, --manifests list.txt, or --manifests items.parquet --manifest-key url
    an earlier run --pages OUT/pages

    Any fsspec path works: local, s3://, hf://. Manifests need the pybookget extra (pybookget); --existing-ocr also keeps the library's own OCR as ocr_original. PDF files are read by the PdfReader block (extra pypdfium2).

    For large collections, fetch the images once, then transcribe, then bind the pages into items:

    uv run pipelines/harvest.py --manifests items.parquet --manifest-key url OUT --tasks 16 --rate-limit 5/1
uv run pipelines/transcribe_modular.py --pages OUT/pages OUT2 --recipe squiddle --item-shards 64
uv run pipelines/bind.py OUT2/pages OUT3 --recipe item-texts

    📦 Output¶

    Output For
    🗂️ Page records (JSON Lines, Parquet) later pipelines: every intermediate result
    🏛️ ALTO, PAGE-XML, hOCR libraries and viewers: every word with its position
    📝 Markdown, HTML, DocLang, Docling JSON documents with headings, tables and formulas
    📜 verbatim_txt per item the text as printed, for checking against a transcription
    📖 readable_txt, readable_md per item reading and training: letterforms folded, hyphens joined, paragraphs flowed

    The text as written is always kept; readable text is derived from it. All text is Unicode NFC; spelling is never modernized. Rejected pages go to rejects/ with the reason. Every run is traced with OpenTelemetry into OUT/traces/ (nothing is sent anywhere unless you set the OTEL_* variables), and linecaster traces OUT shows where the time went.

    🌍 Run anywhere¶

    Where Flags
    💻 this machine none: models load inside the pipeline
    🖥️ this machine, with a model server --backend served
    🧮 a Ray cluster --on ray --tasks 64
    ☁️ Hugging Face Jobs --on hf-jobs --commit <sha>

    On Ray and HF Jobs every task gets one GPU and starts its own model server. A rerun into the same output folder runs only the tasks that didn't finish.

    A model server that stays up 
    P="--layout pp-doclayoutv3 --lines pp-ocrv6-medium-det --recognition kraken-ppocrv6-medium"
uv run pipelines/transcribe_modular.py serve $P
uv run pipelines/transcribe_modular.py scans/ out/ $P --endpoint http://127.0.0.1:8100/v1

    For a vision-language model, --recognition-endpoint points transcribe_vlm.py at a running vLLM or SGLang. Servers listen on loopback only.

    Ray

    ray runs Ray's own command line with the pipeline's packages, so every machine has the same versions:

    uv run pipelines/transcribe_modular.py ray start --head --num-gpus 8
uv run pipelines/transcribe_modular.py scans/ out/ $P --on ray --tasks 64

    Images and output must be on storage every machine can reach.

    Hugging Face Jobs

    One GPU per Job; each Job installs Linecaster at a pushed commit with the pipeline's pinned dependencies.

    uv run pipelines/transcribe_modular.py s3://bhl-open-data/images hf://buckets/<ns>/<bucket>/<run> $P \
  --paths-file hf://buckets/<ns>/<bucket>/pages.txt --env FSSPEC_S3_ANON=true \
  --on hf-jobs --commit <sha> --tasks 4000 --workers 64

    --workers Jobs run at once. --flavor l4x4 --gpus 4 runs four tasks per Job. --dry-run launches nothing.

    ✍️ Your own pipeline¶

    A pipeline is a list of blocks; datatrove runs it. This is the modular pipeline, cut down:

    from datatrove.executor import LocalPipelineExecutor
from linecaster.backends import InProcess as P
from linecaster.blocks.composition import (
    Composer, Recomposer, Typographer)
from linecaster.blocks.layout import LayoutDetector
from linecaster.blocks.lines import (
    LineAssigner, LineDetector)
from linecaster.blocks.readers import ImageFolderReader
from linecaster.blocks.recognition import LineRecognizer
from linecaster.blocks.text import UnicodeNormalizer
from linecaster.blocks.writers import PageFileWriter

pipeline = [
    ImageFolderReader("scans/"),
    LayoutDetector(P("linecaster_paddlex:PaddleLayoutEngine")),
    LineDetector(P("linecaster_paddlex:PaddleLineEngine")),
    LineAssigner(),
    LineRecognizer(
        P("linecaster_kraken:KrakenRecognitionEngine")),
    UnicodeNormalizer(),
    Typographer("ratios@1"),
    Recomposer("unicode-recomposition@1"),
    Composer("docling-composition@1"),
    PageFileWriter("out/", formats=("md", "alto")),
]
LocalPipelineExecutor(
    pipeline, logging_dir="out/logs").run()

    Every block declares what it reads and adds, so a pipeline is checked before it starts: a recognizer without lines fails at once, with every problem listed. Put the script in pipelines/ with the # /// script block of pipelines/transcribe_modular.py (it brings the engines) and build it with linecaster.runtime.run.main to get the pipelines' command line on every machine. The pipelines reference covers backends, partial runs (--until, --after) and the builder.

    🧩 How it works¶

    1. One record per page. Every step reads the page's Transcription and adds its part: regions, lines, text, tables, a document. Steps share the data model and nothing else.
    2. Contracts. Each block declares what it reads, adds, replaces or removes; the builder checks the pipeline and draws its graph from them.
    3. Backends. A model step runs InProcess, Served (a model server reached through saturate, which keeps the GPU busy) or Chat (a vision-language model behind an OpenAI-compatible server).
    4. Executors. datatrove splits the pages into tasks, runs them locally, on Ray or on HF Jobs, and resumes where a run stopped.

    Models batch only the lines of one page, and model revisions and numerically relevant libraries are pinned, so a page's output never depends on the machine or on what else runs. Different GPU types can still differ in rare single characters.

    🧰 Models and blocks¶

    Every configuration is a preset in Linecaster's catalog: an engine, a model at a pinned revision with its original model card, and settings. Released editions never change. Vision-language models run behind vLLM or SGLang; the other models run inside the pipeline or behind linecaster serve, one package per engine: linecaster-kraken (kraken), linecaster-paddlex (PaddleX) and linecaster-tesseract (Tesseract).

    🍳 Recipes¶

    Recipe Pipeline Presets
    item-texts bind.v1 unicode-recomposition@1, latin-historic@1, docling-composition@1
    squiddle transcribe_modular.v1 pp-doclayoutv3@1, pp-ocrv6-medium-det@1, kraken-ppocrv6-medium@1, slanet-plus@2, pp-formulanet-plus-l@1, ratios@1, unicode-recomposition@1, latin-historic@1, docling-composition@1
    The blocks
    Family Block What it does
    Readers ImageFolderReader Reads one page per image file of a folder or bucket.
    Readers ImageParquetReader Reads one page per row of Parquet files with an image column.
    Readers ManifestReader Reads one page per image of each item's manifest: IIIF Presentation 2 or 3, or METS with MODS (also inside an OAI-PMH response).
    Readers PageRecordReader Reads the page records an earlier run wrote (JSON Lines or Parquet), so a pipeline can add one more part.
    Readers PdfReader Reads one item per PDF file, one page per PDF page in order, each rendered to a lossless WebP image.
    Layout LayoutDetector Detects the layout regions of every page, with their labels and reading order, by a layout engine.
    Lines LineAssigner Assigns the lines detected on the whole page to the layout regions and orders them row by row.
    Lines LineDetector Detects the text lines of every page, with their geometry, by a line detection engine.
    Recognition FormulaRecognizer Recognizes every formula region as LaTeX by a formula engine.
    Recognition LineRecognizer Recognizes the text of every line by a line recognition engine.
    Recognition PageRecognizer Recognizes every page with a chat VLM or a page engine, whose output becomes the page's transcription.
    Recognition RegionRecognizer Recognizes each layout region of every page with a chat VLM, one request per region crop.
    Recognition TableRecognizer Recognizes the structure of every table region by a table engine.
    Conversion ImageConverter Converts each page's delivered image into the working image with an image engine and writes it.
    Conversion ImageFetcher Loads each page's image again from its address, for the blocks that need pixels.
    Conversion TranscriptionConverter Reads the transcription file that comes with each page (ALTO, PAGE-XML, hOCR or plain text) into a named transcription.
    Text CharacterNormalizer Normalizes the texts of every line, paragraph and table cell by a normalization engine, next to the text as written.
    Text UnicodeNormalizer Normalizes the as-written text of every line and word to one Unicode normalization form, NFC by default.
    Composition Composer Composes the DoclingDocument of a page or an item by a composition engine.
    Composition Recomposer Recomposes the running text of a page or an item into paragraphs by a recomposition engine.
    Composition Typographer Determines the typographic hierarchy of every page by a typography engine.
    Binding Binder Binds each item's page records, in order, into one item record.
    Binding Splitter Splits each item record into its page records again, in the item's order, with what the item-level blocks added.
    Validation PageValidator Marks the page records that do not validate against Page or lack a required part with an error each.
    Validation RecipeStamper Stamps the recipe edition a run follows on every step of every transcription, of a page or of each page of an item record.
    Servers ChatModelServer Starts a chat VLM server (vLLM or SGLang) inside the task for its Chat backends, through saturate's Engine.
    Servers ModelServer Starts linecaster serve inside the task for its served model blocks, through saturate's Engine.
    Servers ServiceServer Starts the service a page engine's preset names inside the task, and stops it when the task's pages are through.
    Writers ImageFilesWriter Writes each page's image bytes as they came, one file per page.
    Writers ItemDocumentWriter Writes the document of each item record, one file per format: Markdown, text, HTML, DocLang, JSON.
    Writers ItemTextWriter Writes the text variants of each item record as JSON Lines or as files.
    Writers PageFileWriter Writes one file per page and format: ALTO, PAGE-XML, hOCR, text, Markdown, HTML, DocLang, JSON and more.
    Writers PageJsonlWriter Writes the page records as JSON Lines, one file per task, or into item shards for a later stage.
    Writers PageParquetWriter Writes the page records as Parquet, one file per task.
    Writers RejectWriter Writes every page that carries errors to the task's rejects file and passes every page on.
    Composites ModularTranscriber Reads a page's lines the modular way: layout, lines on the whole page, line assignment, line recognition.

    🛠️ Development¶

    To Run or write
    test the core uv run pytest (GPU and network tests skip where those are missing)
    test an engine package uv run tests/test_engines_catalog.py engines/<engine>/tests
    regenerate the docs uv run linecaster docs (--check in CI)
    check released catalog editions uv run linecaster catalog verify
    build the docs site uv run --group docs mkdocs build --strict
    add a model linecaster catalog pin <id> --hf <repo>, a preset in presets/<step>/, linecaster catalog release <id>
    add an engine a package under engines/ that imports only linecaster.data and linecaster.engines.api; test it with linecaster.testing.check_engine
    add a block a PageBlock with process_page(doc, page) and a contract(); test it with linecaster.testing.check_block

    The code lives in src/linecaster/, the catalog in src/linecaster/catalog/data/, the engine packages in engines/, the pipeline scripts in pipelines/. Measurements and decisions are in NOTES.md.

    🏷️ Versions¶

    The current release is v0.1.0; CHANGELOG.md lists each release's changes, upgrade notes first. While the version is 0.x, a release may break things without a deprecation period. The docs site keeps a version per release, latest for the newest, and dev for main.
