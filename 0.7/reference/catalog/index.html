    The catalog: models, presets, recipes¶

    The catalog describes every model Linecaster can run, how it runs it, and the tested combinations. Its entries live in one folder, src/linecaster/catalog/data/, shipped with linecaster; linecaster.catalog reads, validates and resolves them.

    src/linecaster/catalog/data/
  models/<id>/model.yaml, model.md        # + upstream/<revision>/ (the upstream card, verbatim)
  presets/<step>/<id>.yaml, <id>.md       # one folder per step (STEPS)
  recipes/<id>.yaml, <id>.md
  catalog.lock
src/linecaster/catalog/schemas/<kind>-<n>.json    # generated from the Pydantic models

    What the catalog holds¶

    The catalog and its docs are organized by five kinds: engines and pipelines (code, by versioned id) and three kinds of catalog entry (models, presets, recipes; a YAML file each).

    Kind Is Named Lives in
    engine code that implements one step: runs a model, or applies rules versioned id: kraken.recognition.v1, typography.ratios.v1 engines/<engine>/ (a package each); chat.v1 and the rule-based engines in linecaster (linecaster.engines)
    model one upstream artifact at pinned revisions, with its card slug: kraken-ppocrv6-medium models/<id>/model.yaml
    preset an engine, a model pin and the engine's options, ready to use slug, with an edition: kraken-ppocrv6-medium@1 presets/<step>/<id>.yaml
    pipeline code: a shape with slots and the run-anywhere command line versioned id: transcribe_modular.v1 (the script's name) pipelines/<name>.py
    recipe a named combination: a pipeline, a preset edition per slot, options slug, with an edition: squiddle@1 recipes/<id>.yaml

    Besides these: the lock (released editions) and the run record (OUT/run.yaml, and per page in each StepInfo: what a run resolved).

    Ids and versions¶

    Term Whose Meaning Example
    version upstream what upstream calls it, verbatim, never parsed PP-OCRv6 medium, Chandra 2
    revision upstream the exact identity of the files HF commit, version DOI, git commit, sha256
    edition linecaster integer per preset or recipe, raised when outputs can change edition: 3
    .v<n> linecaster the contract of an engine's options or a pipeline's slots and options transcribe_modular.v1
    schema linecaster the format of a YAML file linecaster.preset/1
    release linecaster the package version (run records only) 0.4.0
    • Slugs (models, presets, recipes): lowercase [a-z0-9.-]. They may contain upstream names (deepseek-ocr-2), never our versions. Ids are unique across presets and recipes, so a name means one thing.
    • Code ids (CODE_ID): lowercase dotted names ending in .v<n>. An incompatible change is a new id (.v2); the old one stays registered. Adding an option is compatible when its default keeps the old behavior; changing a default, removing or renaming an option is not.
    • A reference is id@edition; id alone means the current edition. Run records always store the explicit edition and its hash.
    • A tag or branch is resolved to a commit when a model is pinned; the tag is kept as tag: for information. Zenodo: the version DOI identifies the files, the concept DOI is information. Downloads without a commit: the file's sha256 is the revision.

    Files¶

    A model, preset or recipe is a YAML file, the data, validated strictly by linecaster.catalog.schema (unknown keys are errors), and a Markdown file of the same name next to it, the prose for people (why these settings, limitations, changes), without front matter. Tools read only the YAML; the docs generator also includes the prose. The prose is optional, except for presets and recipes with support: core. The lock is YAML only, and so is an evidence record (kept outside the catalog, below). Bulk data (page records, exports) is JSON Lines or Parquet, not catalog data.

    Format Schema id JSON Schema
    model linecaster.model/1 schemas/model-1.json
    preset linecaster.preset/1 schemas/preset-1.json
    recipe linecaster.recipe/1 schemas/recipe-1.json
    evidence (not catalog data; its schema ships here) linecaster.evidence/1 schemas/evidence-1.json
    lock linecaster.lock/2 schemas/lock-2.json
    run record (OUT/run.yaml, not catalog data; its schema ships here) linecaster.run-record/1 schemas/run-record-1.json

    Every YAML file names its format twice: its first line is # yaml-language-server: $schema=<relative path to src/linecaster/catalog/schemas/<kind>-<n>.json> (for editors), and its field schema holds the schema id (for tools). The JSON Schemas are generated from the Pydantic models (linecaster catalog schemas); the test suite fails when a committed one differs from a fresh one.

    YAML has 1.2 semantics, read with ruamel.yaml through linecaster.catalog.yamlio: only true / false are booleans (NO stays Norwegian), and a duplicate key is an error. Values that look like numbers or versions are quoted ("1.0"). Commands that write a file back (release, pin) keep its comments.

    Model (models/<id>/model.yaml)¶

    Field Meaning
    id, version our slug; upstream's name, verbatim
    source kind (hf, zenodo, git, url) and ref (repo id, concept DOI, repository URL, download URL)
    pins one entry per upstream revision: revision, tag, doi, pinned (date), files (name → sha256:<hex>), card, card_sha256, license_file
    license SPDX id where there is one, else the license's own name
    languages, scripts ISO 639-3 (mul for many), ISO 15924
    params parameter count, as upstream states it
    derived_from ref and relation (mirror, converted, quantized, finetuned)

    The upstream card is always copied, verbatim, at the pinned revision, whatever its license: Hugging Face README.md, the HTRMoPo record, a repository README; a separate license file next to it. Its sha256 is in the pin. Cards are never edited; license, languages and scripts in model.yaml are taken from them where they say. A new upstream revision is a new entry in pins, with its own upstream/<revision>/ folder. Model entries are written by linecaster catalog pin.

    Preset (presets/<step>/<id>.yaml)¶

    Field Meaning
    id, edition, step the step must match the folder
    model id and revision of a model pin
    submodels further pins of a multi-model engine, by role
    engine the engine's id: engine: kraken.recognition.v1
    options the engine's options (its Options model)
    settings prompts, sampling and other request settings (chat presets; repair: the repair pass's max_tokens, 0 for off, and temperature)
    labels native layout label → DoclingDocument label; unmapped labels are text
    by_script a by-script engine's strategies: ISO 15924 script code → preset id@edition of the same step, and "*" → the default for every other script (required)
    serve the server it was validated with: server (vllm, sglang, linecaster, vendor), version, image (with digest, for HF Jobs), flags, env, revision_flag, pin_ignore, server_packages, draft (speculative decoding); a vendor's service also command, health, weights_dir (page engines)
    capabilities unit (line, region, page, item) and produces (the parts it adds, vocabulary PARTS)
    provenance derived_from (sources of the settings, each at a commit or revision), authored_by, created
    support, superseded_by see Support

    Recipe (recipes/<id>.yaml)¶

    Field Meaning
    id, edition
    pipeline the pipeline it fills: pipeline: transcribe_modular.v1
    presets slot → preset id@edition (always an explicit edition)
    options the pipeline's options, by name
    provenance, support, superseded_by as for presets

    A recipe's environment and entry point is its script recipes/<id>.py (see Pipelines, recipes and launch.py); a recipe a derivative runs lives in this catalog too (squiddle).

    Measurements live elsewhere¶

    linecaster is not a data repository: the catalog holds no measurements, and neither do the docs. An evaluation (a derivative's, an evaluation project's) keeps its own records, in its own repository, and names what it measured by edition and hash. linecaster provides the format and the tooling to produce them:

    • The evidence format (linecaster.evidence/1, linecaster.catalog.Evidence, schemas/evidence-1.json): one measurement per file, preset: id@edition or recipe: id@edition, context (for a preset measured inside a pipeline: the rest of it), source (own-run, card-claim, vendor-benchmark), dataset (repo@revision, or a description for claims), metrics, date, hardware, software (linecaster commit, server version, backend: in-process or served), run, notes. Claims are never measurements.
    • What a measurement names: the run record (OUT/run.yaml: the recipe edition and its hash, every block's parameters, pipeline_sha256) and the recipe and preset editions stamped on every step of every page.
    • What it measures: the page records (every transcription with its steps' measurements: seconds, tokens, device), the traces (linecaster traces OUT: time per block and page) and the per-page and per-item files.
    • Ground truth and reference transcriptions: ManifestReader(existing_ocr=True) and the TranscriptionConverter read a library's own ALTO, PAGE-XML, hOCR or text into a named transcription (ocr_original, ground_truth, ...) of the page record, next to ocr_new; the writers turn page records into datasets (JSON Lines or Parquet page records, ALTO, PAGE-XML, hOCR, text).

    Scoring (CER and the like) is the evaluation's own; linecaster has no scorer.

    Released editions are immutable¶

    linecaster catalog release <id> writes the current edition's resolved functional content and its sha256 into catalog.lock (per entry: sha256, previous_sha256 where a catalog migration changed it (a list, oldest first, after several), released, linecaster commit, resolved; a recipe edition also pipeline and pipeline_sha256, below).

    • A preset's functional content is what can change outputs: step, the model pin and every submodel pin (id, revision, files), engine, options, settings, labels, by_script (each strategy's edition with that edition's hash, as a recipe names its presets) and serve. A by-script preset is released only on released strategies. Only what the YAML file states counts, so a new optional schema field changes no hash. The Markdown prose, provenance, support level and capabilities are not part of it.
    • A recipe's functional content is its pipeline, each slot's preset edition with that edition's hash and the options it states. A recipe is released only on released preset editions, so one recipe edition pins a whole run down to the weights' files.

    linecaster catalog verify (and tests/catalog/test_catalog.py) fails when a released edition's content changed; such a change is a new edition. Old editions stay resolvable from the lock after the file moves on. Unreleased editions are drafts.

    A recipe edition's expanded pipeline¶

    A recipe names a pipeline id, presets and options; what runs is the pipeline its script builds from them. The lock keeps that too: release builds the recipe's pipeline (its pipeline script with --recipe id@edition on placeholder folders, in-process, one task) and records pipeline, every block with its class and its functional parameters (engines with their options, presets with their hashes; pipelines), and its pipeline_sha256, the hash a run record of that recipe names. verify builds every released recipe edition's pipeline again and reports drift: a block, a parameter or a default that changed in code changes the hash, and verify names the blocks that differ.

    Building it needs no engine: the describe mode (linecaster.runtime.run.describe) builds the recipe's pipeline shape (linecaster.pipelines) in the current process, and blocks and backends import no engine before warm_up(); a preset whose engine is not installed names the engine's class from the repository's engine packages (catalog.code). So verify runs in the core environment, and its hash is the one a run of the pipeline script with its engines records.

    Drift is resolved like any change of a released edition: a change that can change outputs gives the recipe a new edition; a change of the code that keeps behavior (a renamed parameter, a new option whose default keeps the old behavior) is recorded anew with linecaster catalog release <id> --migrate-pipeline. A recipe edition released before pipelines were locked gets its pipeline on its next release (a catalog migration: the edition and its sha256 stay). The lock format stays linecaster.lock/2: the two fields are optional, and only recipe entries have them.

    Catalog migrations¶

    A change of the catalog's own vocabulary or format that keeps every output as it was (a renamed step, a renamed pipeline id, a new file format) is a catalog migration: every released edition keeps its number, its resolved content is rewritten in the new terms and its hash recomputed, and the hash it had before stays in the lock as previous_sha256 (after a second migration a list of both, oldest first). A run record names id@edition and that edition's hash at the time; it resolves by either hash (Catalog.resolve(ref, sha256=...), resolve_recipe, by_sha256, linecaster catalog show sha256:<hex>). A change that can change outputs is never a migration: it is a new edition. A recipe that comes to name, as presets, what its pipeline already ran (squiddle@1 naming the rule-based presets its pipeline ran through the option text: reflow) is a migration too: the pipeline it expands to is the same blocks with the same parameters, so the edition keeps its number, and catalog release --migrate-pipeline records the expanded pipeline again (the recipe stamp carries the new hash).

    Steps, capabilities, labels¶

    Steps (STEPS): layout, lines, recognition, tables, formulas, whose engines run models, and the rule-based steps (RULE_STEPS) image (the working image), normalization (character fidelity: as written → normalized), typography (the hierarchy from type sizes), recomposition (running text from the rows: paragraphs) and composition (the document). Recognition reads a unit (capabilities.unit): line (kraken, PaddleX, Tesseract), region (a VLM per layout region) or page (a VLM or a page engine reads the whole page: a page preset, which launch.py runs by name); a rule-based engine reads a page or an item (the pages of one item, in order). OCRD_STEPS maps the steps to OCR-D's functional steps for METS agents where OCR-D has one (image: preprocessing/optimization, typography: layout/segmentation/classification, composition: layout/analysis); the others are post-processing (recognition/post-correction).

    What depends on the code belongs to the engine (capabilities on the class), e.g. kraken's word boxes with confidences. What depends on the weights belongs to the model or preset: languages, scripts, output format.

    Engines¶

    An engine is a class registered under its id in the entry-point group linecaster.engines ("kraken.recognition.v1" = "linecaster_kraken:KrakenRecognitionEngine"), or one of linecaster's own (BUILTIN_ENGINES): chat.v1 (VLM presets, served only: SERVED_ONLY; the Chat backend), the single-region layout and the rule-based engines. It declares engine_id, step, Options (a Pydantic model whose fields have descriptions; the docs come from it) and capabilities, and takes the pin as weights (and submodel_weights), fetched and checked by linecaster.catalog.fetch. Engine packages carry code only; their presets and models are in this catalog.

    chat.v1's Options (linecaster.adapters.ChatAdapter.Options) are what a run may set over a chat preset's settings (Chat(..., overrides=...), --set recognition.<option>=<value>): max_tokens, temperature and top_p over settings.sampling, repair_max_tokens and repair_temperature over settings.repair (the repair pass; off unless repair_max_tokens is above 0, which must then be larger than max_tokens; a list of rising caps is one repair pass each; lightonocr-3-0.8b@3 sets [8192, 12288], the other presets leave it off), and repetition_detection over settings.sampling.repetition_detection (repetition detection: on by default wherever the preset's server is vLLM 0.17.0 or later, false off, true the defaults, repetition_detection.<field>=<value> for one of min_pattern_size, max_pattern_size, min_count; refused for another server).

    Engine packages (engines/<engine>/: linecaster-kraken, linecaster-paddlex, linecaster-tesseract, linecaster-indra, linecaster-surya, linecaster-services) have versions of their own and a range of linecaster releases they work with (linecaster>=0.1,<0.8), and import from linecaster only the data model (linecaster.data) and the engine API (linecaster.engines.api): the Engine protocol, Capabilities, and the weight helpers weights_of (a model pin as weights), hf_file and hf_snapshot (a Hugging Face pin's files, checked) and model_entry (a model's catalog entry); tests/test_import_rule.py reads the packages with ast and fails on any other import. They are not on PyPI: a preset whose engine is not installed is a CatalogError that names the package that provides it and the pipeline scripts whose environments install it (catalog.code.install_hint). Each package has its tests in engines/<engine>/tests/ (conformance through linecaster.testing.check_engine, and its own units), run in an environment that has it (uv run tests/test_engines_catalog.py engines/<engine>/tests; the page engines' packages: uv run tests/test_page_engines_catalog.py engines/<engine>/tests, the environment of pipelines/transcribe_page.py).

    Page engines and their services¶

    A page engine is an engine of the recognition step whose unit is the page (capabilities.unit: page): it gets the page image and returns the page's transcription, text-only, its raw output verbatim in extra["raw"], as a chat preset's completion is kept. PageRecognizer runs it like any model block (InProcess, or Served through linecaster serve); pipelines/transcribe_page.py is its pipeline. Where the engine talks to a service, its preset's serve block names it and ServiceServer starts it in the task:

    serve.server The service Fields
    vllm vllm serve <the model pin, fetched> --host --port <flags> --served-model-name <the Hugging Face id>, for an engine package that attaches to vLLM (surya.recognition.v1) version, image, flags
    vendor a vendor's page pipeline in its own image (falcon.recognition.v1, oxr.recognition.v1): the image's entrypoint image (by digest), command (the entrypoint), env, health (loopback URLs that must answer 200, in order), weights_dir (where the model pin is downloaded first, when the image reads the weights from a folder)

    The engine's endpoint option (where its service is) is operational: presets leave it to its default (the service's loopback port), a pipeline sets it for a running service (--recognition-endpoint), and the pipeline's hash leaves it out.

    The single-region layout¶

    layout.single-region.v1 (linecaster.engines:SingleRegionLayoutEngine, preset single-region@1) is a layout engine without a model: one region covering the page image (label text, id page, reading order 0; both options), recorded as a layout step. It has the model engines' call (__call__(image, transcription)), so LayoutDetector("single-region@1") runs it, and like the rule-based engines it is built in and runs in the pipeline's process only. pipelines/transcribe_modular.py --layout single-region reads a page as one region.

    Rule-based engines¶

    The engines of the rule-based steps (strategies) live in linecaster.engines, are pure Python and run in the pipeline's process only (IN_PROCESS_ONLY; linecaster serve refuses them): image.webp-lossless.v1, normalization.latin-historic.v1, typography.ratios.v1, recomposition.unicode.v1, composition.docling.v1, and the by-script engines normalization.by-script.v1 and recomposition.by-script.v1. Each has no weights; its Options turn the rules' thresholds into options whose defaults are the values the rules have always had, and it declares scripts: the ISO 15924 scripts it covers (Latn, Hebr, ...), "*" for all. The rules themselves stay in linecaster.text, linecaster.images and linecaster.formats; the engines are thin.

    The call per unit (linecaster.engines.base): page unit __call__(t: Transcription, **options) -> Transcription; item unit __call__(pages: list[Transcription], **options) -> list[Transcription] (an item's pages in order; a page is an item of one page); the image step takes and returns the image's bytes (__call__(data, **options) -> (bytes, info)). Options given to a call override the engine's for that call. Each records a StepInfo with its engine id, its options as settings and its counts as measurements; the block that runs it adds the preset edition and its hash, seconds and datetime. The item unit of the composition is item_document(pages, name, ...): an item's document is no transcription.

    Their blocks take a preset (id@edition) or an engine spec (InProcess("module:Class", **options)), with options over either, like model blocks but without a backend choice: ImageConverter(output_folder, preset) (image), CharacterNormalizer(preset) (normalization), Typographer(preset) (typography), Recomposer(preset, unit="page"|"item") (recomposition), Composer(preset, unit="page"|"item") (composition). The presets of the squiddle recipe's rules: working-image@1, latin-historic@1, ratios@1, unicode-recomposition@1, docling-composition@1. Running text or the page as laid out is the presence of a Recomposer: the Composer composes from paragraphs when there are, else from lines (diplomatic composition).

    Scripts and dispatch¶

    A preset whose engine is a by-script engine names its strategies in by_script: an ISO 15924 code per script that needs its own rules, "*" for every other script.

    id: hebrew-latin-recomposition
step: recomposition
engine: recomposition.by-script.v1
by_script:
  Hebr: hebrew-recomposition@1
  "*": unicode-recomposition@1

    engine_spec resolves them into the engine's strategies (each strategy's engine, options, edition and hash). The engine (ScriptDispatch) routes each decision to the strategy of the script around it: for a decision at a row end (a division mark, the separator between two rows) the script of the last character before the row end that has one, else of the first after it (characters of the scripts Common and Inherited, such as spaces, hyphens, digits and combining marks, have none); for a normalization, each run of a text in one script (Common and Inherited characters stay with the run before them). A script without a strategy of its own goes to "*". Scripts are Unicode's Script property, matched with the regex package's \p{Script=...}. verify checks that every strategy is an edition of the same step and covers its script.

    Pipelines, recipes and launch.py¶

    Every pipeline script declares PIPELINE, its id: its file name with .v<n> (harvest.v1, transcribe_modular.v1, transcribe_vlm.v1, transcribe_page.v1, bind.v1). A script with slots also declares SLOTS (slot → option; the option is the step's name: --layout, --lines, --recognition, ...; the rule-based steps are slots too: transcribe_modular.v1 has --typography, --recomposition, --normalization (the readable item texts' normalization, for --item-texts) and --composition, bind.v1 --recomposition, --normalization and --composition; a slot left empty leaves its step out, e.g. no recomposition: the page stays as laid out). It has no default presets: the user fills every slot, or names a recipe (--recipe id[@edition]), with single flags on top recorded as overrides in the run record (recipe: the edition, the pipeline id, the hash and the overrides).

    The recipes: squiddle (transcribe_modular.v1: PP-DocLayoutV3, PP-OCRv6 line detection and kraken's PP-OCRv6 recognition, tables, formulas and the rule-based steps) and item-texts (bind.v1: unicode-recomposition@1, latin-historic@1, docling-composition@1, the item stage's default combination). Each has its script, recipes/<id>.py (architecture): its environment, with exactly the engine packages its presets need, and its entry point. recipes/squiddle.py is the environment with kraken; pipelines/transcribe_modular.py leaves kraken out.

    uv run launch.py NAME IMAGES OUT [options] launches a recipe or a page preset by name: a recipe runs its script recipes/<id>.py, a page preset the pipeline script of its kind (transcribe_vlm.v1 for chat page presets, transcribe_page.v1 for page engines' presets), each in its own environment, with --recipe or --recognition. serve and ray pass through for recipes. A preset that is one step of a pipeline gets a hint instead: the pipeline, the flag and the recipes that use it.

    Support¶

    core (maintained, validated), experimental (works, may change), legacy (kept resolvable; superseded_by: names the replacement).

    Commands¶

    Command Does
    linecaster models [--step STEP] lists the presets (and the recipes)
    linecaster catalog pin ID --hf REPO [--revision REV] pins a Hugging Face model: model entry, card, file hashes
    linecaster catalog pin ID --github OWNER/NAME --revision COMMIT --file F [--tag T] pins files of a GitHub repository
    linecaster catalog release ID [--commit SHA] [--migrate-pipeline] freezes the current edition of a preset or recipe in the lock, a recipe with its expanded pipeline
    linecaster catalog verify checks the files (schema lines, prose next to its YAML file), the JSON Schemas against the models, cards, pins, released editions and their hashes, recipes and their expanded pipelines
    linecaster catalog show REF the resolved functional content of a preset or recipe edition (id@edition, or a hash, today's or a previous one), with its hash
    linecaster catalog schemas [--out DIR] regenerates the JSON Schemas (default src/linecaster/catalog/schemas/)
    linecaster docs [--out docs] [--readme README.md] writes the generated docs (the catalog's pages among them; not in git, written before the site is built)

    The catalog's generated pages are grouped by kind: docs/catalog/{engines, models, presets/<step>, pipelines, recipes}/ and an index. Engine and pipeline pages are read from the source (linecaster.catalog.code, with ast), so the engines need not be installed. The pages quote no measurements.
